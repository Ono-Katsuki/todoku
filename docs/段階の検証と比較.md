# 段階の検証と、ほかの道具との比べ

2026-11-03。世界調査（目録からの標本、`world/results.jsonl` の 2026-11-03 17:07 の写し）の段階を、とどくとは別の読み方で確かめ、
同じ標本で、エージェントがふだん使う道具（MarkItDown・openpyxl・pypdf・python-docx）と比べた。
都合の悪い結果もそのまま書く。数と表は `world/validation/`（`summary.json`・`grade_check.json`・`compare.json`・`sample.json`）。

## 要点

- **読む段階の一致は、重み付きで 51%（95% 区間 42〜61%）**。一つ違いまで含めて 62%（52〜72%）。食い違いはほぼすべて
  「とどくの方が厳しい」側（49%）で、「甘い」側は重み付きで 0%（0〜10%。数では 125 件中 3 件）。
- 段階ごとに見ると、**S（9/9）と A（26/27）は合う**。**B（4/23）・C（0/32）・F（4/19）は合わない**。
  E は 10/15。
- 合わない理由のいちばん大きなもの（46 件）は、**様式でない書類（統計表・データ・報告）で、見出しの後ろや空のマスを
  入力欄の候補として数え、B・C に下げる**こと。中身はほぼ正確に読めている（窓の中身が正確な書類は重み付きで 90%）。
- **不具合を 7 つ見つけた**（下の「不具合」）。中身を落とすもの（PDF の「ll」の欠け、表計算の行のまとめで値のある行が消える）、
  開けるのに F にするもの（.xls の図形の位置での例外）、0 ページの PDF を A にするもの など。
- **調査に記録された段階は、一つのコードから出たものではない**：同じ書類を、調査を動かしていたコードの写しで付け直すと、
  125 件中 39 件が変わる（A・B → C が 32 件、開けない → 例外 7 件）。調査の途中でコードが変わり、記録は混ざっている。
  また、その時点のコードはコミットされていない。
- **ほかの道具との比べ（同じ 125 件）**：中身の再現率（字の平均）は とどく 0.927・MarkItDown 0.926・ふだんの読み方 0.849 で、
  **読む中身そのものでは、とどくは MarkItDown と並ぶ程度で、勝っていない**（PDF と .xlsx では MarkItDown の方が高い：とどくの
  「ll」の欠けと行のまとめの不具合のため）。差が出るのは、**表示の形式**（12 件中 とどく 12 件・ほかは 1 件）、**計算結果の印**、
  **非表示であることの印**、**.doc・.rtf**（MarkItDown・python-docx は開けない）と、**書くこと**：openpyxl で 1 つのセルに書いて
  保存すると、.xlsx 19 件のすべてで何かが黙って消えた（図形 339 個・画像 8 個・印刷の設定・拡張の要素 1,042 個・ピボット・
  名前の定義 など）。とどくは 19 件とも、書いた所のほかの部品をバイト一致で残した。フォームの欄のない PDF には、pypdf は
  書けない（0/19）が、とどくは 19/19 書き、元のバイト列を前にそのまま残した（電子署名のある PDF でも）。

## 1. 段階の検証

### 設計

- **枠**：調査の結果の写し（10,762 行、段階の付いた 7,656 件。SHA-256 は `sample.json` の `frame`）。調査は続いていたので、
  この時点で固定した。
- **層**：調査の群（pdf・sheet・text・csv）× 記録された読む段階。20 層（D の段階は調査では1件もない：D はエージェントの判断
  （書く値のぼかし）でしか付かないため。pdf:S・text:E なども 0 件）。
- **抽出**：層ごとに、種 `20261104:層` で候補を並べ替え、前から取り直して、SHA-256 が調査のときと同じものを、層ごとに 8 件まで
  使う（小さな層は全部）。取り直しは robots.txt を守り、同じ相手には 3 秒の間、1 本ずつ。128 件を取り、3 件は中身が変わって
  いたので同じ層の次の候補に替えた。**125 件**。
- **重み**：層の書類の数 ÷ 使えた数（逆確率）。全体の割合は重み付きで、95% 区間は「推定 ± 1.96·SE（層ごとの分散を
  Agresti–Coull の p̃ で見積もる）」。層の中が全部一致・全部不一致だと、層の中で取り直す bootstrap の区間は幅 0 になる
  （`ci95_bootstrap` にも残した）ので、こちらを主に使う。段階ごとの割合は重みなしの Wilson の区間。
  csv:S の層（2,687 件）が全体の 35% の重みを持つので、全体の数は CSV の影響が大きい。重みなしでは 53/125（42%）。
- **調べたとどく**：調査を動かしていたコード（作業ツリーの `src/todoku`、コミットされていない変更を含む）の写し。
  木のハッシュ `00ad4239…`。worktree の HEAD（4bb59f4）のコードは ZIP を読めず、調査と比べられないため。
- **参照の読み**（とどくを使わない）：openpyxl（数式と保存された値の両方）・xlrd（.xls、結合・非表示の行も）・pdfplumber と
  pypdf（字・画像・(cid:) の字・フォームの欄）・python-docx と XML の直読み（.docx の段落・表・テキストボックス・
  コンテンツコントロール）・OpenDocument の XML・macOS の textutil（.doc・.rtf）・CSV は文字コードを決めて読むだけ。
  openpyxl が開けない .xlsx（1 件）は XML を直に読んだ。
- **比べ方**：NFKC と空白の除去のあとで、字の多重集合の再現率、参照の単位（セルの値・行・段落）が並びを保って窓にある割合、
  2 字の並び（bigram）の再現率（落ちた字を見つける）、表計算は番地ごとの値、窓の「同じ形の行」のまとめに消えたセル、
  PDF は画像だけのページ・字に直せない字・フォームの欄。食い違いは、確かめる人が窓と参照の両方を見て（PDF はページの絵も）、
  どちらが正しいかを決めた（参照が誤りの例：7z の書庫を Latin-1 で読んだ CSV、textutil が残す制御文字）。
- **判断の基準**：段階の定義（`src/todoku/grade.py` の冒頭と README の表）をそのまま当てはめる。
  S＝データそのもの（CSV）、A＝規則で正確に読める（入力欄がない・すべて作り手の印）、B＝正確に読めるが、入力欄の一部が配置からの
  推定か規則では決められない、C＝規則で再現しない処理（値を変えるマクロ・確かめられない数式）、E＝字のない画像の中身、
  F＝開けない・中身の字が読めない。様式でない書類（統計表・報告）に入力欄はないものとした。
  あわせて「段階の理由が事実として正しいか」（claim_true）と「窓の中身が正確か」（window_faithful）を別に付けた。
- **確かめた人**：1 つの AI エージェント（このリポジトリの作業をしたものと同じ系統のモデル）。人の評価者 2 人の独立な評価ではない。

### 食い違いの原因（読む段階、72 件）

| 原因 | 件数 |
|---|---|
| 様式でない書類で、見出しの後ろ・空のマス・字の間の空白を入力欄の候補として数え、B・C に下げた | 46 |
| .xls の図形の位置の読みで例外になり、開けるのに F（不具合 1） | 7 |
| スキャンの画像の圧縮（JBIG2・JPX）を todoku が開けないことを、書類の F にした（書類は E） | 4 |
| グラフだけのシート・印刷範囲が外れたシートを「画像だけのシート」として E（不具合 5） | 5 |
| 字に直せない字が箇条の記号だけなのに F | 2 |
| 定義では B（規則では決められない所）なのに、コードは C | 3 |
| その他（Big5 の文字化けを C、NUL のある CSV を F、0 ページの PDF を A、ZIP の中の HTML・XML を F、画像だけの Word を B） | 5 |

**定義とコードの食い違い**：`grade.py` の冒頭では B が「一部の欄が配置からの推定か、規則では決められない」だが、
`_agent_reason` は「規則では決められない所」を C にする。記録の C（32 件）の多くはこれだけが理由で、定義どおりなら B
（様式でない書類では A）。

**記録の混ざり**：記録で A・B だった 32 件は、同じ書類をいまのコードで付け直すと C になる（見出しの後ろを
「規則では決められない所」とする規則が、調査の途中で入った）。記録は、取り直しの前に付けた段階と、後の段階が混ざっている。
調査の地図・割合は、この混ざりを含む。

### 不具合（再現の手がかり）

1. **.xls が「開けない（F）」になる**：e-Stat の .xls 7 件（例 https://www.e-stat.go.jp/SG1/estat/Xlsdl.do?sinfid=000015170657 ）。
   xlrd は開ける。`xls/book.py` の `_place` で `KeyError: 'r1'`：OfficeArt の図形に位置（0xF010）がない（グループの中の子の図形
   など）と、位置の辞書に r1 がなく、ブック全体の読みが止まる。調査の sheet:F の 15 件中 12 件が .xls の「開けない」。
2. **PDF の窓で「ll」の片方が落ちる**：同じ字の重ね書き（太字に見せるもの）を 1 字にする判定（`pdf/layout.py`、中心の差が
   字の大きさの 1/4 より小さい）が、幅の狭い字（l）の隣どうしを重ねとみなす。例 https://api-proxy.edh-cde.dfo-mpo.gc.ca/catalogue/records/58a5280d-0dea-4004-b2cf-719936d3f8dd/attachments/Reference_Table.pdf
   の「(All Temperature Windows)」が窓では「(Al Temperature Windows)」（ページの絵で「All」を確かめた）。ほかに
   イタリア（「delle」→「del e」）・英国（「collections」→「col ections」）・パキスタンの PDF。重ねとして数えるので、
   とどくの「読み落としがない」の検査にもかからない。同じ書類で、字の「_」が入力欄の印に置き換わり、窓の字から消える。
3. **表計算の窓で、値のある行が「同じ形の行が続きます（入力欄はすべて空欄）」にまとめられて消える**：`xlsx/window.py` の
   `reading` は空欄の行だけをまとめるはずが、値のある行もまとめる。例 https://opendata.gov.nl.ca/public/opendata/filedownload/?file-id=16992
   （707 行のうち 699 行、値のあるセル 20,271 個が Markdown の窓に出ない）。ほかに 4 件（3,238・557・247 個のセル、
   注記の文 5 行）。段階は A のままで、エージェントは中身がないと読む。
4. **0 ページと読んだ PDF を、理由なしの A にする**：https://data.gov.ua/dataset/01de86b7-2a7f-492e-9d01-c9824b444290/resource/3660a7cb-2b98-4405-9b11-4959dc3cd3b9/download/13-01-2023-preiskurant-tsin-z-terapevtichnoyi-ta-khirurgichnoyi-stomatologiyi.pdf
   （pypdf は 4 ページの画像を読む。pdfminer も 0 ページ）。窓は空で、段階は「規則だけで正確に読める」。
5. **「画像だけのシート」の誤り**：グラフ（セルの値から描くもの）だけのシートを画像と同じに数える（例 https://data.london.gov.uk/download/ep8ow/a7a69c22-150c-49f3-a1fd-90d4c24d98d4/tfl-journeys-type%20(2).xlsx 。
   とどくの窓自身がグラフの値の表を出している）。印刷範囲が使っている範囲の外にあるシート（セル 1,316 個）も「画像だけ」にする
   （https://data.gov.hr/ckan/dataset/8111eb66-38b4-4c47-b2d7-6759695b4c79/resource/0aacd4eb-2d41-4388-8178-4ba8a11cf8c3/download/statisticki_pregled_2022_konacna_za-webfinal.xlsx ）。
6. **NUL バイトのある CSV を「読めない（F）」にする**：https://prodavnicasunce.rs/cenovnik/cene_proizvoda_QVATTRO_COMPANY.csv
   （UTF-8・区切り「;」・29,790 行。値の欄に NUL が 53,085 個）。窓には中身がすべて出ている。
7. **テキストの文字コードの候補が UTF-8・Shift_JIS・EUC-JP だけ**：Big5 の注記（https://www.censtatd.gov.hk/en/data/stat_report/product/B1010006/att/B10100062026AN26B01.zip
   の中の 數據用戶須知.txt）を Latin-1 として読み、文字化け（窓に注意は出る）。段階は C で、その部分は実際には読めない。

不具合ではないが段階を左右するもの：JBIG2・JPX の画像を開けないことを書類の F にする（書類はスキャン＝E）。
字に直せない字が箇条の記号（Wingdings）の 9〜12 字だけでも F。Word には「画像だけ」の規則がなく、説明のない画像 16 枚だけの
文書が B になる。非表示のシート・行の中身は Markdown の窓に出ない（「JSON の窓にある」と書いてあるが、MCP の read_window では
読めない）。

## 2. ほかの道具との比べ

### 設計

- 同じ 125 件で、道具ごとに別の処理で読む・書く（2 GB・120 秒で止める。止まったものはなかった）。
- **とどく**：窓（Markdown の全部分）と `api.fill`。**MarkItDown**（0.1.9、`markitdown[all]`）。**ふだんの読み方**：
  .xlsx は `openpyxl.load_workbook(p)`（既定）・.xls は xlrd・PDF は `pypdf` の `extract_text`・.docx は python-docx の段落と表・
  CSV は UTF-8 で開くだけ。書き方は openpyxl（読み込み→代入→保存）・python-docx（マスの `text` に代入→保存）・
  pypdf（`update_page_form_field_values`）。Docling など大きな機械学習のモデルを使う道具は、この PC の負荷の決まりで入れていない。
- 中身：参照の単位に対する字の多重集合の再現率と、2 字の並びの再現率（落ちた字が分かる）。読めなかった書類は 0。
  **PDF の参照は pdfplumber（pdfminer）で、MarkItDown と同じ字の取り出しなので、PDF では MarkItDown に有利**。
  適合率は、出力を区切りで切った断片が参照にある割合（表計算は数の見た目が道具ごとに違うので数えない）。
- 特徴：その書類にある（参照で調べる）ときだけ数え、出力がそれを伝えているか（字があるか・印があるか）を数える。

### 書く

とどくが書ける所（入力欄、または規則では決められない所）を示した書類に、1 つの値を書いた（.xlsx 19・.xls 9・.docx 4・PDF 19。

## 限界

- 確かめたのは 1 つの AI エージェントで、人の評価者 2 人の独立な評価（κ）ではない。様式かどうか・入力欄があるかの判断には
  人による揺れがありうる。判断はすべて `judgments.json` に理由とともに残した。
- 125 件。層ごとに 8 件までなので、段階ごとの区間は広い。D の段階は調査に 1 件もなく確かめていない。
- 標本はオープンデータの目録からで、様式（申請書）がほとんどない（フォームの欄のある PDF は調査全体で 3 件で、どれも欄は
  電子署名だけ。標本には 0 件）。とどくの得意な「様式に書く」場面、PDF のフォームの欄・チェックボックス・XFA・Word の
  コンテンツコントロールへの書き込みは、この標本では測れていない。
- 時間の比べは公平でない：とどくは窓を作る時間だけ、ほかは Python の起動とライブラリの読み込みを含む。
- 参照の道具も誤る（7z を Latin-1 で読む、制御文字を残すなど）。食い違いは確かめたが、両方が同じ誤りをする所（例：同じ
  字の並びの取り違え）は見つからない。
- 表計算の数の値は、窓の見た目（書式つき）と参照の生の値で形が違うので、番地ごとの比べは窓の JSON で行い、Markdown の窓に
  出ているかは「同じ形の行」のまとめで消えたセルの数でだけ確かめた。
- 書類は確かめたあと作業用のフォルダに残し、リポジトリには URL・SHA-256・数・短い説明だけを置いた。
