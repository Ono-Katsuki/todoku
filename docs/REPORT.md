# とどく：詳細レポート

使い方・道具の説明・形式ごとの作り・検査の読み方・比較の条件をまとめた。評価の計画は [再評価の計画](再評価の計画.md)、全結果は [ポータル](https://claude.ai/artifact/45P2GdSFYWkAqWrdLebmSH)。

[English](REPORT.en.md)

**要約**

- 185 か国・地域の政府サイトの書類 935 件を、版を固定してから実際に読み書きした（878 件は固定まで誰も開いていない新しい標本）。正確に読める文書は推定約 245 万件、正確に書ける文書は推定約 238 万件。
- 比べる道具の数は、人が形式ごとに最良の道具を選び、書く欄をとどくが教えた上限の数だ。それでも比べる道具は、書くでは .doc・.xls が 0 件、読むでは .doc・.odt・.ods・.rtf が 0 件で、.xlsx は書くが 29 対 11、読むが 35 対 14。元の PDF のバイト列を残すことを条件にすると、書ける文書はとどく約 238 万件、比べる道具約 192 万件。
- とどくは、書いた所とその計算結果のほかは変えていないことを、書類ごとに証明する。比べる道具には、この証明の仕組みがない。

## 測定の結果（`eval-freeze-2`）

道具は `eval-freeze-2`（86bba80）、採点は事前に登録した v2 です（[再評価の計画](再評価の計画.md)）。書類は 185 か国・地域の 935 件（一覧は [`sources/eval_freeze2/world.tsv`](../sources/eval_freeze2/world.tsv)）。

- **878 件（161 か国・地域）**：固定するまで誰も開いていない新しい標本。選んだ 900 件のうち、保存が途中で切れていた 22 件を除いた数です。
- **57 件（24 か国）**：候補が 50 件以下の層で、調査の書類から、結果を見ずに種とハッシュの順で選びました。固定版の比較と 11 件重なります。とどくは読む 39 件、書く 38 件が通りました。

### 分かっている弱点

- **とどくだけ書けなかった PDF 39 件（878 件のうち）**：認証の署名を守って断った 約 5 件（正しい断り）、きれいに書けたのに確かめの OCR が読み違えた 約 15 件、欄でない写真・ロゴの上に書いた 約 12 件、印刷された字に重なった 約 5 件、読みにくくなった 2 件（暗い背景に黒、ページの端で切れる）。内訳は目で分けた数です。
- **欄でない所を欄として示す**：様式でない書類で、写真やロゴの上を書く所として示すことがあります。
- **読みにくい所にも書く**：PDF に書いた字は 1 字ずつ下地と比べ、下地と同じ色で見えない字は読み戻しの違いとして止めます。暗い下地の上の字と、後から描かれるものが重なる字は、止めずに書いて、位置（mm）と一緒に知らせます。写真や模様の上の字が読めるかは、エージェントが view_page で見て決めます。
- **読む段階が甘い所**：S・A と出して正解の基準に届かなかった書類が 19 件。アラビア語の PDF 5 件（字はそろうが 2 字の並びが .89〜.97。比べる道具は .47〜.63）、.ods・.odt 4 件、画像の字の PDF 3 件（字の再現率 0.2 で A の例がある）、基準のすぐ下（.989〜.995）7 件。
- **Excel の計算**：全体の再計算は書く時に使う計算器と同じものです（別の計算器との突き合わせは入力を変えた 3 通り・306 セル）。`INDIRECT`・`OFFSET`・`TODAY` など依存先が決まらない関数は数えるだけです。大きなブックの経路を実物で試したのは 3 個で、.xlsm は 0 個です。大きなブックに書いたあと、ブック全体の計算（別のプロセス）が書いた値と違うと分かると、検査（audit_document）がそのファイルを「名前.unverified.拡張子」に付け替えます：付け替えるのは検査を呼んだときで、それまでは元の名前のままです。ほかのプログラムが開いているなどで付け替えられないときは、名前はそのままで、渡さないように伝えるだけです（作ったファイルでだけ確かめた）。同じシートの同じ名前のチェックボックス・ドロップダウン・リストボックス・スピンボタン・スクロールバーは、id に部品の位置を付けて分けます（「Check Box 1@B6」。オプションボタンの組と同じ決まり。位置のない名前で書くと、候補を示して断ります）：集めたブックのうち開けた 377 件の部品 2,975 個に、名前のぶつかるこれらの部品は 1 個もなく、作った .xlsx でだけ確かめた（.xls も同じ決まりを通るが、名前のぶつかる .xls は作っていない）。ActiveX の部品には位置を付けません（Excel がシートの中で名前を 1 つに決める）。

- **記号の書体の限界**：記号の書体（Symbol・Wingdings・Wingdings 2・Wingdings 3・Webdings・ZapfDingbats）で書いた字は、書体ごとの対応表で Unicode の字として読む（.docx・.doc・RTF・.odt と、埋め込みの数式（MathType）の Symbol の字。表とスライドは次の項。対応表は、Adobe の Symbol・ZapfDingbats の表と、Wingdings・Webdings を Unicode に入れたときの提案書 WG2 N4384 から）。対応表にない番号と、文書が記号の書体と宣言した、対応表のない書体（Marlett・MT Extra・JustUnitMark など）の字は、私用の領域の字（U+F0xx）のまま外字として伝え、読む B にする（.txt・.pptx・.hwpx・.hwp・一太郎の外字も、同じに伝える）。記号の書体の宣言は、書体の表の 1 つずつの書体で見る（.docx の `w:charset` 02、.doc の chs 2、RTF の `\fcharset2`、.odt の `style:font-charset="x-symbol"`）：同じ名前の書体が、宣言のあるものとないもので並ぶ文書がある。LibreOffice が変換した文書は、記号の字「©」を「記号の書体と宣言した Arial の字」として書くので、外字として伝える。見ていない所：.docx の表のスタイルの書体、.doc の文書の既定の書体、Word 6.0/95 の .doc、RTF の箇条書きの段の書体（印の字は `\listtext` の字から読む）。チェックを入れる字を書体ごとの番号で書くのは、.docx の `w:sym` と箇条書きの印だけで、箇条書きの印の箱は、.docx の、チェックのない箱だけを欄にする。書いた字は、記号の書体を引き継がない（引き継ぐと、書いた字が、その書体の絵やギリシア文字になる）：.docx・.doc は字の書式から記号の書体を外し、RTF はその前に選ばれていた書体に、.odt は外側のスタイルの書体に戻し、結果でそう伝える。段落のスタイルが記号の書体を決めている所（.docx・.doc）と、戻す書体のない所（RTF・.odt）には、そのまま書き、読み直した字が書いた字と違えば書き出さない。集めた書類では、段階が変わったのは 530 件のうち 15 件（どれも仕様書の .txt で、外字を伝えるようになって A から B）、Word の書類 494 件の窓の字で変わったのは 11 件の箇条書きの印の字だけ（「●」が「⚫」、「➢」が「⮚」、「■」が「◼」、私用の領域の字が「•」：合わせて 160 個）で、書く所は同じ。記号の書体の字のすぐ後ろに書く所があるのは 1 件（石綿の健康診断の様式の「医師の氏名㊞」の 2 所。㊞ が JustUnitMark の字）。
- **記号の書体の限界（表・スライド）**：Excel の表（.xlsx・.xlsm と、.xls の BIFF8）は、セルの書式の書体と、文字の中の字ごとの書体（.xlsx の `rFont`、.xls の字ごとの書式）が記号の書体（対応表のある書体か、文字セットが 2 の書体）の字（U+0021〜U+00FF と U+F020〜U+F0FF）を、その書体で読んだ字で、窓・欄・見出し・読み直し・検査・試算の結果に出す（大きな表の道も同じ）。セルの値は保存された字のまま持ち、数式・試算・マクロは保存された字を使う（`=COUNTIF(B1:B2,"þ")` は、窓に「🗹」と出る Wingdings のセルを数える）：数式の中に書かれた字は、保存された字のまま示す。書くときは、見える字で頼む。その書体にある記号は、その書体の番号の字で書く（「🗹」は「þ」）。その書体が別の記号として描く字（Wingdings の「A」は「✌」）は、書かずに断る。その書体が読み替えない字（かな・漢字・「✗」など）は、そのまま書き、ほかの書体で描かれると伝える。数・日付・真偽の値は書いて、その書体で表示される形を伝える。チェックの箱の字は、その書体の箱の番号の字で付け外しする。読み替えない所（保存された字のまま出る）：.xlsb・.ods・Excel 5.0/95（BIFF5）とそれより前の .xls の記号の書体、条件付き書式が変える書体、エラーの字、再現できない表示形式の値。表示形式が足す字は、字ごとの書体ではなくセルの書体で読む。PowerPoint（.pptx）は、字（`a:r`・`a:fld`）の書式の `a:latin` が記号の書体なら U+0021〜U+00FF の字を、`a:sym`（なければ `a:latin`）が記号の書体なら U+F020〜U+F0FF の字を、その書体で読む。書いた字には、Word と同じに、記号の書体を引き継がない（字の書式から記号の書体の指定を外し、結果でそう伝える。書き換えなかった字は元の書式のまま）：チェックの箱は、ふつうの字（☐・■ など）で書く。.pptx で読み替えない所：箇条書きの印（`a:buFont`・`a:buChar`：.pptx の箇条書きの印と番号は、前から窓に出していない）、図形の `lstStyle`・レイアウト・マスター・テーマから受け継ぐ書体（`+mj-lt` などの参照）、`a:ea`・`a:cs` だけに指定した記号の書体、`a:sym` だけを指定した U+00FF までの字。確かめ方：どれも作ったファイルで確かめた。集めた表 393 件（.xlsx・.xlsm・.xls・.ods）に記号の書体のセルはなく、窓・欄は前と同じ（変わった所 0、CPU 時間 729.5 秒 → 732.3 秒。全部を 1 つの窓にすると時間のかかる 2 件は、範囲で読んだ結果が前と同じ）。.pptx は集めた書類にない。.xls は、同じ .xlsx を LibreOffice が書き出したファイルで確かめた（LibreOffice は、「☑」・「山田」・U+F0FC のセルを、Wingdings でない書体にして書き出した）。LibreOffice 26.8 の Calc は、Wingdings・Symbol・Wingdings 2 のセルの U+00FF までの字を記号として描き、その書体が読み替えない字をほかの書体で描いた。Impress は、`a:sym` の私用の領域の字（U+F0FC は ✓、U+F0E0 は矢印）、Symbol の「abg」（αβγ）、Wingdings 2 の「RT」（☑☒）を記号として描いたが、`a:latin` が Wingdings の「þ」「¨」「ü」「q」と Wingdings 2 の「þ」は、字のまま描いた：とどくは、Word・Excel の文書と同じ決まり（記号の書体の U+0021〜U+00FF の字は、その書体の記号）で読む。Excel・PowerPoint そのものでは確かめていない。

- **表のセルに字で指定する数と日付の限界**：字で指定した数は、小数点「.」・3 桁ごとの桁区切り「,」の書き方で読む（JSON の数と、窓が示す数と同じ書き方）。ほかの書き方で、数としての読み方が 1 つに決まる形（「1.234,56」「1.234.567」「1,5」「1 234,56」「1'234.56」「12,34,567.89」）と、ほかの文字の数字（Unicode の十進の数字：「١٢٣」「१२३」など。アラビア文字の小数点・桁区切り・％と、マイナス記号 U+2212 も）は、Excel が字として受け取る形なので、数の表示形式のセル・数式から参照されるセル・数の入力規則のあるセルでだけ数にして、どう読んだかを伝え、ほかのセルでは書いたとおりの字にする（日付の表示形式のセルでは数にしない）。「1.234」「10.000」「1,234」の形（1〜3 桁の数字、「.」か「,」、3 桁の数字）は、小数点と桁区切りの字が逆の地域では値が 1000 倍違う：決まった書き方で読み、どう読んだかと、もう一方の値の指定の仕方（JSON の数）を伝える。セルの表示形式が、書いた字と同じ数字と記号で表示するとき（`#,##0` のセルの「1,234」、`0.000` のセルの「1.234」）は伝えない：小数点が「,」の地域の書き方のつもりで、`#,##0` のセルに「1,234」を指定すると、1234 として書き、そのことを伝えない。通貨記号は、Unicode の通貨記号（Sc）1 つを、数字の前か後ろで読む（「円」「EUR」などの語は読まない）。かっこの負の数「(100)」・後ろの符号「100-」は読まない（数の入るセルでは、字として書いたことを伝える）。日付は、年が先頭の形（「2026-04-01」「2026/4/1」「2026年4月1日」「2026년 4월 1일」「2026.04.01.」と、同じ形のほかの文字の数字）と和暦（「令和8年4月1日」「R8.4.1」：先頭の英字 M・T・S・H・R は日本の元号として読む）だけを読む。年は西暦として読む（仏暦・ヒジュラ暦・民國の年を、西暦に直さない）。月の名前（「April 1, 2026」）・民國の元号・日付と時刻を続けた形（「2026-04-01T10:00」）は読まず、日付のセルでは字として書いて伝える。年が先頭でない数字の日付（「03/11/2026」「1.4.2026」）は、日付のセルでは断る。Excel の日付の始まりの日（1900 年 1 月 1 日。1904 年から数えるブックは 1904 年 1 月 1 日）より前の日付は、字として書いて伝える（.ods では日付として書き、見える字は ISO の形のままにする）。
- **PDF に書いた字の重なりの確かめの限界**：書いた字が、印刷された字・罫線・ほかの書いた字に重ならないか、欄を出て欠けないかは、字形の輪郭の四角で確かめる。書いたファイルに書体を埋め込んだ字（同梱の Noto Sans JP・字を組み立てて描く文字・埋め込んだシステムの書体）は、その書体の字形の輪郭から。埋め込まない Helvetica の字（ラテン文字の拡張の一部：ş・ł・ę など）は、Adobe の字形の表（AFM）の値で、見る道具が代わりの書体で描くと少し違う。埋め込まない CJK の書体の字（ハングル・簡体字・繁体字）と、印刷された字の側は、見積もりの四角のまま（基線から上へ字の大きさの 0.7 倍）。書く側は、墨が欄の上下を出るときは基線を寄せ、墨の高さが欄より高いときは、字を 0.5 pt ずつ小さくする。小さくしたことを知らせるのは、元の 6 割より小さいときと 6 pt 未満のときだけ（「Égjy」を 12 pt で、高さ 14.4 pt の所に書くと 11.5 pt になり、知らせない）。1 字ずつ書く欄は、いちばん広い字の送りがマスの幅に入る大きさにする。書いたものどうしは、どちらも輪郭の四角のとき、小さいほうの四角の 1/4 以上が重なれば断り、それより小さい重なりは、位置（mm）と一緒に知らせる。見積もりの四角のある値は、少しでも重なれば断る。基線より下に出る字（g・j・y など）を、すぐ下に罫線のある所に書くと、罫線がかかる知らせが出る：集めた PDF 819 件の 116,128 か所に「Égjy」「gj」「j」を書くと 4,330 か所（日本語の値では 1,253 か所）。日本語の値では、書く位置は 1 か所も変わらない。
- **PDF に書いた字の見え方の確かめの決まりと限界**：書いた後のページを、書いた部品の所だけ 100 dpi で描いて、書く前の絵と比べる。①部品の四角の中で画素が 1 つも変わらなければ、読み戻しの違い。四角の全体で、変わった画素の明るさの比が 3:1 より小さければ、知らせる（ここまでは前と同じ）。②描いた字の 1 字ずつについて、その字を描く直前の下地の色と、字の色を重ねた後の色を、字の画素ごとに比べる：どの画素も下地と同じ色になる字は「描いても見えません」として読み戻しの違い、インクの半分より多くが明るさの比 3:1 より小さい所にある字は、その比と位置（mm）を知らせる。③字を描いた直後の色と、ページを描き終えたときの色が、インクの半分より多くで違う字は、「後から描かれるものが重なっています」と位置を知らせる（ほかの注釈・重なった欄）。フォームの欄の見た目に描いた字と、欄のないページに描いた値の両方を見る。同じ欄の部品がページにいくつかあるときは、どの部品も見る（前は、1 つ目だけ）。静的な XFA のフォームに書いたときは、同じ名前の PDF の欄の見た目を見る（前は、見ていなかった）。字は、欄の書体の指定（/DA）の色で描く：文字の欄・コンボ・リストと、見た目のない書類に足すチェックの印（前は、いつも黒。集めたフォーム 24 件の部品 1,652 個のうち、5 件の 274 個が、黒でない色（#000080 が 272 個・赤が 2 個）を指定していた）。確かめ方：集めた PDF 84 件の 703 か所に「検査 Ab1」を書くと、668 か所の 2,800 字を字ごとに見て、見えない字は 0、暗い下地の知らせは 2 件の 3 か所（15 字。どれも、濃い灰色の帯・箱の上の黒い字で、前の決まりは知らせなかった）、重なりの知らせは 0（残りの 35 か所は、①で知らせた 8 か所と、PDF の欄のない XFA の 27 か所）。字ごとに見る・見ないで、84 件の確かめの時間は 99.4 秒と 99.3 秒。作ったファイルで、黒い帯の上の字（止める）・濃い青の帯の上の字（知らせる）・細い線の上の字（知らせない）・後から重なる注釈（知らせる）・暗い欄に白い字の指定（知らせない）を確かめた。限界：とどく自身の描画で決める（ほかのビューアーの絵は見ない）。書体が手元になくて字を描けないページは、字ごとには見ない（画素が 1 つも変わらないときに、確かめられなかったことを知らせる）。字ごとに見るのは、色で塗って描く字だけ：模様で塗る字・輪郭だけの字は、①の決まりだけ。チェック・ラジオの印、字を囲む ○、印影の画像は、見え方を確かめない。後から重なるものが半透明でも「重なっています」と知らせる（隠れたとは限らない）。写真や細かい模様の上の字は、画素ごとの明るさの比で決めるので、人の読みやすさと合わないことがある。100 dpi より細かい違いは見えない。描画が 1 ページ 15 秒・全体 45 秒を超えると、確かめられなかったことを知らせる。動的な XFA（PDF の欄のないフォーム）は、とどくがページの絵を描けないので見ない。とどくが欄のないページに描く値と、とどくが作る欄は、黒で描く。
- **PDF の切り抜き（クリップ）の限界**：ページに描かれているが、切り抜きの外にあって見えない字・線は、見える内容として読まない。確かめるのは、切り抜き（`W`・`W*`、部品の BBox、ページの枠）の道の外枠の四角だけ：外枠の外にあるものは見えないと決め、外枠の中にあるものは、切り抜きの形（三角・丸など）の外にあっても、見えるもののまま。見えない字は、読み順・見出し・欄・重なりの確かめに入れず、ページごとの「切り抜きで見えない字」の節に、位置（mm）と一緒に示す（字は落とさない。段階は変えない）。外枠にかかる字は、見える字のまま。外枠のすぐ外（字の大きさの半分以内）の字は、埋め込んだ書体の字形の輪郭が外枠の外にあるときだけ見えない字にし、埋め込まない書体の字は、見える字のまま。そこにある空白（墨のない字）は、同じ文字の組（BT〜ET）の隣の字と同じ側に入れ、空白だけの組は、見える側のまま。直線と塗りの四角は、外枠の外にあれば罫線・マスにせず、外枠をまたげば中の部分だけにする。ページの端では切らない（ページの外へ出る線は、出たままの形）。曲線と、一部だけが切り抜かれた画像は切らない（画像の四角は元のまま。view_image は、切り抜く前の画像を見せる）。字の形で切り抜く書き方（Tr 4〜7）と、道のない切り抜きは見ない。集めた PDF 835 件（各ファイルの初めの 60 ページ）：見えない字は 2,297 字（61 件・111 ページ。見える字は 6,448,166 字）、見えない線・図形は 2,091 個（19 件）、見えない画像は 0。前は、見えない字が見出しや行に混ざり（同じ位置に重ねた別の様式の見出し・枠からあふれた行）、見えない線がマスを作っていた。窓が変わったのは 194 件で、1,151,389 か所のうち、なくなった所 1,501・増えた所 881。
- **PDF の取り消し線の決まりと限界**：PDF の取り消し線は、字の書式ではなく、字の上に描いた線なので、線と字の位置から決めて、その字の後ろに「〔取り消し線：「字」〕」と示す（字は消さない。ページの `struck` に、字・その行・位置）。取り消し線と決めるのは、行の向きに沿った、白くない直線（線・細い塗りの四角。横書きの行は横の線、縦書きの行は縦の線）が、字の四角の中央の半分（中心から、字の大きさの 1/4 まで）を通り、太さが字の大きさの 1/4 までで、両端が、かかる字の並びから 1 字ぶんより外へ出ず、線の長さの半分以上がその並びの上にあり、両端がほかの線・曲線につながらないとき。かかる字は、幅の半分より多くが線の下にある字。かかる字のすぐ隣に続く空白の字（描かれた空白のグリフ。字の間の空きから補った空白ではない）も、同じ決まりで線の下にあれば、並びに入れる（空白ごと選んで消した所は、線が字より長い）。破線は、空きが 1 字ぶんまでならひと続き。下線・マスの縁・表の罫線・字を塗る帯・字より長く続く切り取りの線は、この決まりに入らない。取り消し線と決めた線は、下線の罫線（書く所）にしない。言わないもの：字より 1 字ぶんより長く続く線、斜めの線・曲線・画像の中の線。字の中央を通るが字より長い線は、「取り消し線かもしれない」とも伝えない：集めた PDF では 614 本（73 件・162 ページ）あり、そのうち 524 本は、端がほかの線につながり、長さの半分より少ししか字にかからない線（表の罫線・ページの罫線）。残りのうち、罫線と決まらない 88 本をページの画像と位置で見て、取り消し線は 3 本（選ぶ語「相続人」2 か所と「本人」1 か所。どれも 1 件の手引きの中）で、ほかは、記入例の字が罫線に重なった所・切り取りの線・引き出しの線だった：全部に「かもしれない」と付けると、消していない説明の字を消した字として読ませる。3 本のうち「相続人」の 1 か所は、字のすぐ後ろの空白のグリフが線の下にあるので、いまは伝える。残りの 2 か所（線が、選ぶ語の並ぶ幅いっぱいに引いてあり、字より 1.3 字ぶん・1.7 字ぶん長い）は伝えない。線を描いた順と、塗りで隠れているかは見ない。字の画と同じ位置に描いた線は、取り消し線として伝える。線が幅の半分までしかかからない端の字は、範囲に入らない。取り消した字が長いときは、その字を印の中でもう一度示す。どうして取り消したか（無効・選ばなかった選択肢・訂正）は決めない。集めた PDF 835 件（各ファイルの初めの 60 ページ：6,183 ページ）では、17 件の 96 か所。96 か所の全部をページの画像で見て、93 か所は字の上の取り消し線、1 か所は字の画と重なる線（「事」）、1 か所は箇条の印「•」の上の短い線、1 か所は、空白ごと線を引いて作った切り取りの線（「き　り　と　り　線　印」：字と空白のグリフの中央を線が通るので、字の上の線として伝わる）だった。取り消し線が下線の罫線の所になっていた 12 か所がなくなり、窓のほかの字と欄は前と同じ（変わった所 0）。縦書きの取り消し線は、集めた書類になく、作ったファイルでだけ確かめた。
- **PDF の字の色の決まりと限界**：PDF の字の色は、字を描いたときの塗りの色（輪郭だけを描く字は線の色）。ページごとに、見える字（空白と、見えない描き方の字を除く）の数がいちばん多い色を「ふつうの色」とし（同じ数なら黒）、ふつうの色と違う字に印を付ける：行（マスの中の 1 行）の字がみな同じ色なら行の前に「〔字の色 #FF0000〕」、行の一部ならその字のすぐ後ろに「〔うち字の色 #FF0000：「字」〕」（Word・Excel と同じ記法。字は変えない）。ふつうの色が黒でないページは、ページの `normal_color` と、窓の「このページのふつうの字の色は #FF0000」で伝える（そのページでは、黒い字に印が付く）。色の意味（記入例・注意・リンク）は決めない。色は、選んでいる色空間を通して読む：DeviceGray・DeviceRGB・DeviceCMYK、CalGray・CalRGB、Lab、ICCBased（成分の数で読む）、Indexed、Separation・DeviceN（濃さの関数を計算する）。前は、色空間を見ずに成分の数だけで読んでいた（Separation の濃さ 1 を「白」と読んでいた：字の色は使っていなかったが、取り消し線・罫線の「白い線」の決まりに効いていた）。模様（Pattern：繰り返しの模様・グラデーション）で描いた字は、1 つの色にならないので「〔字の色（模様）〕」。値は RGB に直した値：CMYK・ICCBased・Separation は、ICC プロファイルを使わない決まった式で直すので、画面の色と少し違うことがある。見た目にほぼ同じ色（#000000 と #0D0D0D）も、値が違えば印になる（近い色をまとめるしきい値は置かない）。集めた PDF 835 件・6,183 ページ（各ファイルの初めの 60 ページ）：印は 492 件・3,483 ページに 33,009 個。ふつうの色が黒でないページは 240 件の 924 ページ（#FF0000 が 659 ページ：記入例と注意書きのページ）。どの成分も 32/255 より近い色の印は 207 個（0.6%）、模様の印は 4 個（1 件。グラデーションで描いた字）。印がいちばん多いのは、リンクと用語に色を付けた仕様書（1 件で 1,330 個）。窓の読み順の字は 4.1% 増える（1,538 万字 → 1,602 万字）。印を除いた窓の字と欄は、前と同じ（変わった所 0）。ページの画像で確かめたのは 3 件（黒い帯の上の白い字・全部が赤い注意書きのページ・グラデーションの字）。読まないもの：背景の色（白い字が見えるかは決めない：「#FFFFFF」と伝える）、透明度と重ね方、色空間の既定の置き換え（DefaultGray・DefaultRGB・DefaultCMYK）、Type 3 の書体が字の中で決める色、フォームの部品・注釈の見た目の字の色、画像の中の字。行の一部の色は、字の位置から決める（1 つの字のまとまりの中で色が変わる所は、字の中央の位置で分ける）。
- **PDF の塗り・画像の下の字の決まりと限界**：ページに描かれているが、後から描いた透けない塗りの四角・画像の下にあって、画面にも印刷にも出ない字は、見える字として読まない（前は、見える字と同じに読んでいた：記入例の吹き出しの下に残った元の文・修正の白い塗りの下の字が、読み順・見出しに混ざっていた）。下にあると決めるのは、字の四角（送りの幅 × ## 使い方：MCP サーバーとして

とどくは MCP（Model Context Protocol）のサーバーだ。どの AI エージェントからも使える。

**Claude Code ではプラグインとして入れる。どのフォルダからでも使える。**
MCP サーバーと、申請書を探して記入するときの進め方（スキル `shinsei`）が一緒に入る。

1. Python の道具 [uv](https://docs.astral.sh/uv/) を入れる（とどくを動かすのに使う。とどくは Python の標準の機能だけで動く）。

   ```
   curl -LsSf https://astral.sh/uv/install.sh | sh
   ```

   （Homebrew なら `brew install uv`。対応する環境は macOS で、Windows と Linux はβ）

   初回に uv が Python 3.11（約 30 MB）をダウンロードする。インターネットにつながらない所で使うなら、
   つながる所で先に `uv python install 3.11` を実行する。
2. Claude Code の中でプラグインを入れる。

   ```
   /plugin marketplace add Ono-Katsuki/todoku
   /plugin install todoku@todoku
   ```
3. 新しい版にするときは、ターミナルで `claude plugin marketplace update todoku` と `claude plugin update todoku@todoku` を実行して、
   Claude Code を開き直す（プラグインの版は、リポジトリのコミットで決まる）。

**iPad・スマートフォンから使う**：とどくはパソコンの上で動く。書類はパソコンから出さない。Claude Code の
[Remote Control](https://code.claude.com/docs/en/remote-control) で、パソコンの Claude Code を iPad から操作する。
パソコンで `claude remote-control`（または開いている Claude Code の会話で `/remote-control`）を実行し、iPad の Claude アプリか、
ブラウザーの [claude.ai/code](https://claude.ai/code) からそのセッションにつなぐ。パソコンの MCP サーバー（とどく）とファイルは
そのまま使える。パソコンは付けたままにする（Pro・Max・Team・Enterprise などのプランで使える。API キーでは使えない）。

あとは「寝たきりの私が使える助成を探して、申請書を書いて」「この様式に事業所の情報を入れて」と話しかけるだけだ。
このリポジトリの中で開いたときは `.mcp.json` からも使える。ほかの MCP 対応のエージェントでは次のように設定する。

```json
{ "mcpServers": { "todoku": { "command": "uv", "args": ["run", "--quiet", "--no-dev", "--directory", "<このリポジトリの場所>", "todoku-mcp"] } } }
```

| 道具 | すること |
|---|---|
| `open_document` | 書類を開き、形式・入力欄の数・窓の最初の部分を返す |

| `extract_processing` | 書類の計算の処理を、処理として取り出す。**計算の決まりを知りたいときはこれ**。同じ形の数式を 1 つの規則にまとめ（「D3:D100000 = B{row}*C{row}」）、入力・参照表・出力・順番・分岐・マクロ・PDF の計算まで返す。`format: "python"` で、確かめつきの `calculate(inputs)` のモジュールを書き出す（下の「処理を処理として取り出す」） |

> 本人：「この処遇改善の計画書に、去年と同じ事業所の情報を入れて」

<summary>壊れた書類への備え</summary>

MCP サーバーは、道具の呼び出しを別のプロセス（働き手）で動かす。1 回の呼び出しに時間とメモリの上限を置く（`TODOKU_TIME_LIMIT`・`TODOKU_MEMORY_LIMIT_MB`）。超えたら働き手を止めて、そう返す。

- **Windows（β）**：この分け方（パイプの受け渡し）が使えないので、サーバーの中で動かす。上限は展開・描画・項目の予算（`TODOKU_MAX_ITEMS`）と、時間とメモリを見る見張りのスレッドだ。Python の処理の切れ目で止めるので、C の中の 1 回の処理の途中では止まらない。コマンドラインも同じ予算で動く。
- **macOS**：メモリの上限 RLIMIT_AS が効かない。長い呼び出しは、働き手のメモリを `ps` で外からも見張る。`ps` が使えるかはサーバーの起動時に一度確かめる。使えない環境では、その見張りが効かず働き手の中の見張りだけになることを知らせる。
- **Linux**：`ps` が使えなくても RLIMIT_AS は効く。止まるのは外からの常駐メモリの見張りだけだ。

どちらのときも、標準エラーとサーバーの説明（instructions）でそう知らせる。

## 処理を処理として取り出す（`extract_processing`）

書類からデータだけを受け取れば、処理はエージェントの推測になる。`extract_processing` は、書類の中の計算の決まりを、構造のある完全な形で渡す（Excel の仲間 .xlsx・.xlsm・.xls・.xlsb・.ods など／PDF のフォーム）。標準ライブラリだけで動く。値を AI で決めない。

- **規則**：同じ形（R1C1 で同じ）の数式を、まとまりごとに 1 つの規則にする。`text`（`D3:D100000 = B{row}*C{row}`）・`formula`（ファイルに書かれたまま）・`a1`・`r1c1`（正規形）・読む範囲・セルの数・例外（範囲の中の違う数式と、上書きした定数）を返す。空いたマスを挟むなら別のまとまり、埋まっていて規則のセルの方が多いなら例外。行の多いブックも流して読み、セルごとの控えを持たない（10 万行 × 2 列の数式で規則 4 個・増えるメモリは 24 MB 未満）。
- **構造**：入力（見出しは「左と上にある字」という事実として・読む規則・入力規則）、パラメータ（絶対参照で読まれる値のセル）、参照表（VLOOKUP・INDEX・MATCH・XLOOKUP などが読む範囲。中身をデータとして返し、`read_table` の頼み方を添える）、名前、出力（どこからも読まれないセル）、規則の順番（読むものが先）と循環（セルでも輪か、累計のように順に計算できるかを見分ける）、IF・IFS・SWITCH の分岐の木、配列数式（式のまま。展開しない）、外部のブックへの参照、計算のたびに変わる関数と、静的に分からない所（`OFFSET` の高さが `COUNTA(A:A)` など）、計算に使う隠れたシート・行・列、シートのあいだの流れ。
- **マクロ**：手続きのソース、読み書きするセル（字で決まる所だけ。`Cells(i, 5)` は「E?」、決まらなければ「分からない」）、いつ動くか（`Worksheet_Change` とその見張る範囲、ボタン・図形）、呼ぶ手続き、規則との関係（どの規則の入力に書くか・どの規則の結果を上書きするか）。
- **`format: "python"`**：`calculate(inputs: dict) -> dict` を持つ 1 つの `.py` を書き出す。とどくにも標準ライブラリの外にも頼らない。計算の決まり（丸め・日付・エラー）は計算エンジンのソースから使う分だけ切り出す。同じ決まりの写しを手で持たない。計算できない関数に頼る出力は、理由を言う例外（`NotReproducible`）にする（`outputs` でほかのセルだけ、`on_unknown="mark"` で印つき）。
- **返す前に確かめる**：書き出したモジュールを別のプロセスで（`python -I -S`、とどくを読み込めない状態で）動かし、数式のすべてのセルを、保存された値ととどくの計算の両方と比べる。結果は `verification`：一致の割合、すべての不一致（多ければ別のファイル）、規則ごとの `proven`／`mismatch`／`not_proven` と理由。計算のたびに変わる関数に頼る規則、保存された値のないセル、再現できない規則は「確かめられなかった」と規則ごとに言う。

開発の様式での実測：葛飾・墨田など 23 区の Excel 13 個のうち数式のあるものは 1 個（42 セル → 42 規則、一致 100%。ほかは数式がない）、corpus/forms の 9 個は 149,630 セル → 1,383 規則（一番大きいブックは 105,256 セル → 203 規則）。保存された値・とどくの計算との一致はどちらも 100%。本物の Excel に計算させた値とも、入力を変えた 3 通り・306 セルで差はない。

1 つの値の説明は `explain_calculation`、値を変えた試算は `try_calculation` だ。

<details>
<summary>取り出す範囲（結果の <code>limits</code>）と PDF のフォーム</summary>

条件付き書式と入力規則は、それぞれ規則の種類として並べる（Python の書き出しには入らない）。ピボットテーブル・Power Query（M のソース）・データ接続は「セルの数式で書けない処理」として定義（元の範囲・項目）だけを示し、計算は再現しない（.xlsx・.xls・.ods は定義まで読む。.xlsb はピボットがあることだけを示す）。INDIRECT・OFFSET の依存は静的には分からない（モジュールは実際の参照先で計算する）。動的配列の結果の大きさが変わると、こぼれる範囲は Excel と同じく変わる。

PDF のフォームでは、計算の順（/CO）と欄のあいだの規則（`AFSimple_Calculate`）を同じ形で返し、Python にも書き出す。独自の JavaScript と簡易フィールド記法は、そのまま示して「評価していない」と書く（`evaluated: false`）。

</details>

<details>
<summary>印影・署名の置き方と証明</summary>

本人が**はっきり同意したときだけ**（`"consent": true` がなければ置かない）、本人の印影・署名の画像（PNG・JPEG）を、
字の目印（`{"seal": 画像, "consent": true, "cover": "印"}`）か、ページの枠（`"page"`・`"box"`（mm）。スキャンした紙でも）に置く。
画像は縦横の比を保って枠の中に置く。透けない画像がページの字を隠すときは置かない。

証明は、足したのがスタンプの注釈とその見た目・画像だけで、画像が本人の画像と一致する（JPEG はファイルのバイト列、PNG は開いた画素と透け）ことを確かめる。
`view_page` は置いた画像をページに描いて見せる。

実印・自署（手書き）が求められる所では画像は受け付けられないことがある。そのことを本人に伝える（受け付けられるかは様式の決まりで、言葉の一致では決めない）。Word・Excel には、まだ置けない（証明つきで置く方法を作るまで、書かずに断る）。

</details>

**PDF に書く字は、描ける字形があるものだけだ。** 同梱の書体（Noto Sans JP Regular、SIL OFL 1.1）の字形を部分埋め込みするので、書体のない環境でも同じ字形で出る。描けない字は、白く抜けた見た目を書かずに、理由を添えて断る。

<details>
<summary>字の経路と電子署名</summary>

同梱の書体（日本語・欧文・ギリシャ文字・キリル文字・ベトナム語の字など 16,732 字）に字形のある字は、語や言語によらず、書いた字の字形だけを PDF に埋め込む（増えるのは多くの書類で数 KB〜数十 KB）。

同梱の書体にない字は字ごとに次の経路で描き、結果の `fonts_not_embedded` に残す。

- 欧文の拡張 ş ğ ł ř ő などは Helvetica（WinAnsi と、標準の 14 書体の字形の表にあるラテン文字の拡張）。
- ハングル・簡体字などは埋め込まない CID フォント。CMap（Adobe の公開の対応表、`scripts/make_write_cmaps.py`）で決まる字形が、宣言した字形の集まりの補遺の範囲にあるものだけを使う。
- どちらにもない字は、このパソコンの TrueType の書体（Arial など。`TODOKU_PDF_FONT` で指定。空にすると、同梱の書体も含めて埋め込まない）から、書いた字の字形だけを埋め込む（書体の埋め込みの許しを確かめる）。
- PDF/A と名乗る文書では、埋め込まない書体より、このパソコンの書体を先に試す。
- アラビア文字・ヘブライ文字・インド系の文字・タイ文字は、とどくが字を組み立てて（シェーピング：字の形の選び分け・並べ替え・記号の位置）、このパソコンの書体の字形で描く。このときの確かめは、描いた字形の並びがとどく自身の組み立てと同じかを照らすもので、見た目そのものは確かめていない。そのため、書いた欄は書く段階 B として、エージェントが view_page で画像を見て確かめる（結果の check_visually）。

証明と読み戻しは、値（/V）だけでなく見た目（/AP）の字も読み直し、どの字も描ける字形で、見せるはずの字かを確かめる。

**電子署名された PDF** は、署名が許す範囲だけに書く（固定された欄・変更を許さない認証の署名には書かず、記入だけを許す署名では新しい欄・○を足さない）。署名があれば、書き込みが「署名のあとの変更」として表示されることを本人に伝える。

</details>

## 事実を出し、判断はエージェントに任せる

とどくが決めるのは、仕様書で決まること（ECMA-376・MS-DOC・PDF 32000・Unicode などの決まり）と、壊さないための守り（証明・読み戻し・はっきりした重なりを断る）だけだ。
仕様書で決まらないこと（どの字がその欄の見出しか・書く所か・どこに寄せるか）は、語の一覧や、書類の束に合わせた数で決めない。窓と欄の一覧に事実を出し、エージェントが読んで決める。

<details>
<summary>何を事実として出すか</summary>

- **見出し**は印刷された字のとおりで、切らない。表のマスは左と上のマスの字（`row_label`・`column_label`）と間のマスの数、
  Excel は近くの字とその離れ方（`near`：マスの数と mm）。すぐ隣でない字は見出しとして示さず、「E12（左に 3 列あけて『氏名』）」と示す。
  PDF の空のマスと下線の罫線は、左・上・右・下でいちばん近い字と、所をまたいで続く行の前後の部分（`line_left`・`line_right`）を、離れ（mm）と一緒に示す。
- **「？」の所**には、所の字・字数・幅の目安・前後の字・字間を空けた並びの字数（`facts`）を添える。
- **所の id は位置で決まる**：Word と同じ窓の形式（.docx・.doc・.rtf・.odt・.jtd・.hwpx・.txt・.pptx）の段落の中は
  `P段落.c前の字数`（前に印刷された字が 5 字なら `P12.c5`）、Excel のセルの中は `シート!B3@字の位置`。数え順の番号ではないので、
  ほかの所が増えても減っても、前の所に書いた後も変わらない。PDF は `p{ページ}.{作りの頭の字}{左}-{上}`（mm。`t` 空のマス・
  `m` 空のマスの並び・`g` 行の中の空き・`b` 箱の字・`u` 下線の罫線）で、facts も mm（`rect_mm`・`width_mm`）だ。格子に並ぶ
  空のマスは x・y の並びでまとめて示し、字のあるマスの字の下・上の空きは「［↓余白 12.0 mm］」と示す。
  Word などの古い数え順の id（`P12.1`・`P12.a1`）は、同じ所を指すと決まるとき
  （その段落にその並びの所が 1 つだけのとき）だけ受ける。
- **チェックの値**は `true`/`false` と、その欄が宣言した状態の値（PDF の状態の名前・XFA の値・箱の字）だけを受ける。
  「はい」「有」などの言葉を読み替えない（本人の答えを true/false に直すのはエージェントだ）。
- **書いた値の意味**はエージェントが述べる：`{"value": 値, "as": "生年月日"}`（書類には書かれない）。対話での一覧は
  「生年月日：昭和60年4月1日（p1.t45-112／近くの字「住所」）」、`as` がなければ「p1.t45-112（近くの字「住所」）：…」で、近くの字を欄の名前として
  示さない。本人の確かめる手段は会話なので、本人が確かめる書類ではいつも `as` を渡す（なかった所は `written_without_as`）。
- **字の前・後ろへの差し込み**：Word・Excel なども PDF と同じく `{"@1": {"before": "年", "occurrence": 2, "value": …}}`・`{"@1": {"after": "氏名", "value": …}}` で
  書ける。段落やセルが字で始まる所に、とどくが語の決まりで所を足すことはしない。
- **Word の○**は、既定が字の囲み線（`w:bdr`。□だが字の書式なので位置がずれない）だ。Word はページの上の字の位置を保存しないので、楕円の図形は
  描き手でずれる（`"style": "ellipse"` と明示したときだけ。どちらで書いたかは結果に出る）。
- **置き方と範囲**もエージェントが決める：PDF の `align`（left・center・right）・`pad_mm`・`box`、Word の字を目印にした書き込みの
  `near` の範囲（`near_paras`）。既定（左寄せ・同じ行／同じ話）は、決めないときの出発点だ。
- **書いた後は見て確かめる**：PDF は `view_page` が字の形・線・画像・欄の見た目をページのとおりに描くので、エージェントが書いた所を
  見て確かめる（埋め込まれていないフォントは代わりのフォントで描き、字形のない字は灰色の四角、開けない画像は灰色の枠で示し、
  そのことを結果に書く）。Excel・Word などは描けないので、折り返し・はみ出しの見積もり（書類に書かれていない値を仮に置いたときは
  「仮に」と書く）と、記入した内容の一覧（選んでいない選択肢の組・残っている「？」の所の数も）を対話で確かめる。

</details>

## 確かめていること

### 全て正確に読み書きできるか（`audit_document`）

1. **読み落としがない**：窓を作る処理とは別の読み方で、ファイルの中の文字を全部拾い、窓に 1 つ残らず出ていることを確かめる。
2. **全部の欄に書ける**：窓が示したすべての入力欄に、入力規則に合う試しの値を一度に書き込む。
3. **証明**：書き込み処理の内部を使わず、前と後の 2 つのファイルを読み直して、変わったのが書いた所（と、その計算結果・見た目）だけであることを確かめる。
4. **読み戻し**：書いた後のファイルを読み直して、書いた値がそのまま出ていることを確かめる。

### Excel：書いた所と、その計算結果のほかは変えていない

.xlsx・.xlsm・.xls の書き込みは 2 つの確かめを通す。範囲は `proof_scope` に数で返る。

- **連動の確認**：数式の字（別のシート・範囲・定義名・テーブル・共有数式・配列数式）から、書いたセルに連動するセルを計算せずに求める。連動しないセルの値か数式が元と違えば不合格だ。
- **全体の計算**：書いた後のファイルをブック全体で計算し直し、保存された値と照らす。連動するセルの差は不合格だ。連動しないと求めたセルが書いた値で変われば、連動の見落としとして不合格にする。

大きなブックは、時間の上限（`TODOKU_CALC_SECONDS`）に全体の計算が入らなければ `deferred`（未確認）で返す。書き出したファイルを `audit_document` に渡すと、別のプロセスで全体を計算し、結果を `written_proof` で返す。

<details>
<summary><code>proof_scope</code> の読み方</summary>

- `not_dependent`：書いた値に連動しないセルと、元と同じだったセルの数。
- `dependent`：連動するセルと、変わったセルの数。
- `undetermined`：連動を決められないセル。読む先が計算で決まる数式（INDIRECT・OFFSET・範囲の演算子など）と、開くたびに変わる関数（TODAY・RAND など）は、推測で決めずに数える。
- `recalculated`：全体の計算の結果。`checked`・`same`（照らした数と一致数）、`cannot_calculate`（計算できないので照らしていないセル）、`stale`（書いた値をまだ反映していないセル。開いたときに計算し直す印のあるものなど）。
- 全体の計算は書き込みの部分計算とは別に、全部の行を読んで計算する。計算器は同じ `formula/` なので、関数の実装は Excel の保存値との全数照合で別に確かめる。
- 大きなブックの連動の確認は、元と書いた後のシートの XML を比べる（書き込みの索引を使わない）。
- `written_proof` に `problems` があれば、そのファイルを本人に渡さない。

</details>

### 段階：読む（S〜F）と書く（A〜D）

| 読む | 意味 | | 書く | 意味 |
|---|---|---|---|---|
| S | データそのもの（CSV・JSON） | | A | そのまま書ける（作り手の印のある欄） |
| A | 規則だけで正確に読める（地域で見え方が変わる組み込みの日付の表示形式は、地域によらない ISO 8601 の字で示し、そう伝える） | | B | 解析しないと書けない（配置から推定・窓の「？」をエージェントが判断・文字コードを選んでから書く） |
| B | エージェントが読めば正確（中身は窓にすべて出ていて、決まらない所は窓の根拠でエージェントが決める：文字コードの候補・Excel 以外で保存された計算結果・再現できない段落番号の書式） | | C | 画面（UI）から入力する（ボタンのマクロ・電子申請の画面） |
| C | エージェントが工夫して変換できる（マクロ・確かめられない数式・窓の読み落とし・どの文字コードとしても読めない） | | D | 書けない（アクセスできない・署名・印・拇印・公証など、手で行う所） |
| D | エージェントの解釈が必要 | | | |
| E | エージェントが得意でない形式（スキャン・画像だけのシート・中身が画像の文書） | | | |
| F | アクセスできない | | | |

読む段階は、中身を読むことだけで決める（入力欄の見つけ方は書く段階）。窓とは別の読み方で拾った中身が窓に出ていなければ
（`audit_document` の読み落とし）、読む段階は A・S にならず C だ。文字だけのファイルで文字コードがいくつもの候補で読めるときは、
窓に候補と見本を並べ、エージェントが選んだ文字コードを `encoding` で渡すと、その文字コードで読み直す（選んだことは理由に残る）。
BOM も宣言もなく、UTF-8 でもない 8 ビットの字のファイルは、バイトからは文字コードが決まらない（ドイツ語の Windows-1252 は GBK としても、
タイ語の Windows-874 は Shift_JIS の半角カナとしても、仕様どおりに読める）。とどくは、多バイトの 6 つと 1 バイトの 27 の文字コードのうち、
きれいに読めるものをすべて候補に出し（窓は決まった順の最初のもので作る。読む B・書く B）、決めるのはエージェントだ。
CSV の区切りは、.tsv はタブ、1 行目の `sep=` の宣言があればそれ、なければ「どの行にも同じ数ある区切り」（カンマ・タブ・セミコロン。引用符の中は数えない）。
2 つの区切りがどの行にもそろうときは、決められないと窓と段階で伝える（読む B・書く B）。

判定は「ファイルの構造から確実に分かる規則」か「エージェントが窓を読んだ判断」のどちらかで行い、言葉の一致では決めない。
「押印」という語が書類にあっても、それが「押印不要」かもしれないからだ。押印・自署・電子申請の画面のように意味の要ることは、
とどくが問いとして示し、エージェントが窓を読んで答える。段階は順位付けではない。どう扱えば届くかを示す。

### アクセシビリティの注意（段階とは別）

説明（代わりの字）のない画像は、画面の読み上げを使う人に中身が届かない（WCAG 1.1.1）。
PDF・Word・Excel・PowerPoint・OpenDocument・RTF の画像ごとに、説明があるか、飾りの印があるかを調べ、説明のない画像を、場所（ページ・段落・近くの字）とともに注意として示す。
エージェントは画像の中身を推測で埋めず、本人に場所を伝える。

## 大きな書類

大きいから読む量を減らすことはあっても、読めないことにはしない。窓の全体の見積もりが `TODOKU_CONTEXT_BUDGET_CHARS`（40 万字。20 万トークンの会話に入らなくなる大きさ）を超える書類は、`open_document` が概要（大きさ・ページ・シート・行・何がどこにあるか）を返し、エージェントが要る所を範囲で頼む。小さな書類はいままでどおりだ。

<details>
<summary>続き・上限・控え</summary>

- **続き**：どの結果にも、読んだ範囲（`covered`）・残り（`remaining`）・続きの頼み方（`next`）が付く。たどり終えると全部を読んだことになる。`list_fields` も同じだ。
- **`list_fields` の結果の大きさ**：MCP の結果が `TODOKU_RESULT_CHARS`（25,000 字。Claude Code の上限 25,000 トークンに合わせた大きさ）に入らないときは、書くのに要る事実（id・見出し・種類・選択肢・値・その行の文脈・書き込みの決まりなど）を残し、根拠の事実（`near`・`evidence`・`why` など）を省いて、省いたものと頼み方を `omitted` に書く。`ids` を渡すとその欄の事実をすべて、`detail: true` ならすべての欄を省かずに分けて返す。それでも入らない分は `next` で続く。Python の API とコマンドの結果は変わらない。
- **段階**：費用の小さな確かめは全体で行い、残した確かめは `deferred`（「未確認：全ページの字の読み落とし」など）に示す。見本で決めた段階ではない。
- **長い行・長いマス**：.txt の長い行の `list_fields` は、1 回に 200 万字ぶんを調べて `next` で続く。CSV の 1 マスがとても長いときは、一覧の値は頭の 2000 字で切り、`value_chars` と `value_cut` で切ったことを示す（全部は `read_window`）。
- **検査**：`audit_document` は長い仕事だ（1 回の呼び出しの時間に縛られず、呼ぶたびに進み具合を返し、止まっても控えの続きから進む。控えは `~/.cache/todoku/jobs`、`TODOKU_JOBS_DIR` で変えられる）。
- **控えと個人情報**：長い仕事の控え（作っておいた窓の `.window`・検査の結果・試算の値）には書類の中身が入る。自分だけが読める場所（0700）に置き、最後に書いてから `TODOKU_JOBS_TTL_HOURS`（24 時間）で消す。元のファイルを消したら、その控えも消す。`0` にすると、窓は読んだら、仕事の記録は結果を返したら消す（読まれなかった控えは 1 時間で。大きな書類は開くたびに作り直す）。`todoku forget` で、動いている仕事のほかをすぐに消せる。消えるのはとどくの次の呼び出しかサーバーの起動のときなので、とどくを使わなくなった後に残したくないときは `todoku forget` を使う。パスワードは控えに書かない。
- **上限**：止めるのは壊れた・悪意のあるファイルだ。圧縮の展開は圧縮したバイトに対する比率（`TODOKU_MAX_INFLATE_RATIO`、200 倍）で測り、メモリの上限は物理メモリの 1/4（`TODOKU_MEMORY_LIMIT_MB`）だ。大きさだけではファイルを断らない（`TODOKU_MAX_FILE_MB` を超えるファイルは、写像で読む。PDF の増分更新も元のバイトを流して写す）。止まった呼び出しは、代わりに頼める小さな範囲（`smaller_request`）を伝える。
- **埋め込みの大きな表**：Word に埋め込んだ Excel のブックのうち、窓（`TODOKU_CONTEXT_BUDGET_CHARS`）に入らないものは、開くときには解析しない。`read_window`・`list_fields` に `sheet: "E1!シート"` と `rows` を渡すと、その行だけを解析して返す（`next` をたどれば全部を読める）。書くときの欄の名前は変わらない。検査（`audit_document`）はすべてを読む。窓を作るのに時間の上限を超える書類は、長い仕事（`jobs.py`）になり、進み具合を返す。
- **大きな配列**：シートに入る大きさの配列（`SEQUENCE(1048576,16384)`・`ROW(1:1048576)*COLUMN(A:XFD)`・`EXPAND`・`TEXTSPLIT`・`MAKEARRAY` など）は、マスを作らずに「行・列 → 値」の計算として持ち、頼まれたマスだけ計算する（シートを超えると、Excel と同じ `#NUM!`）。合計・個数・最大などの集計は、形の分かる配列（行・列の番号の多項式）なら式で答え、そのほかは少しずつ順に読む。どのマスの値も途中の和も double でちょうど表せないときは、Excel と同じ行の順に足す（実機で 15 桁まで一致）。ただし 2 億 6 千万マスを超える配列（Excel も持てない大きさ）の和は、正確な値を返してそう伝える。時間の中で終わらない集計は、進んだ所と続け方を伝える（`try_calculation` の `cells`：別のプロセスで控えの続きから進む。`TODOKU_CALC_SECONDS`）。
- **範囲の所**：入力規則・数式の参照・テーブル・配列数式の範囲・OpenDocument の繰り返しが広いとき（1 つの宣言が 16,384 マスを超えるとき）は、1 マスずつの欄にせず「`S!C5:C40000`（空のセル 39,996 個・数式が読む・入力規則 …）」として同じ事実を持つ（窓の「範囲の所」、JSON の `range_places`、`list_fields` の `kind: "range"`）。中のどのマスも番地で読めて書ける。`list_fields` に `sheet` と `rows` を渡すと、その行の分を 1 マスずつの欄で返す（文書に埋め込んだ表は `sheet` に `E1!シート`）。
- **分けて読む道に入る大きさ**：中身のバイトが `TODOKU_LAZY_MIN_KB`（4 MB）より小さな書類は、窓を作ってから分ける。分けて読む道でも、たどり終えると窓の全体と同じ行・同じ欄の id になることを、形式ごとに確かめている（tests/test_lazy_more.py）。ほかのシートの数式に指されたセルの「？」の印だけは、そのシートを読まないと分からないので、大きなブックでは付かないことがある（番地で書ける）。
- **書き込みの守り**：大きな書類の道でも、印刷された字の置き換え・もとからあった値の書き換え・電子署名・手で行う所を、ふつうの道と同じ決まりで結果に出す（tests/test_generalized_guards.py）。大きなブックでは、書いた所の「近くの字」は同じ行の左だけを見る（上の行は読まないので、ないときは「上の行は見ていません」と言う）。まだ空いている欄は数えず、`list_fields` の範囲で頼む。
- **.xlsx の残り**：字の目印に `near` がなくても、共有文字列と行を探して書く。ZIP64 も、行の番号が順に並ばないシートも読める（書くのは全体を読む道。中央の一覧まで 64 ビットの ZIP64 は読むだけで、書くときは理由を添えて断る）。値を変えると動くマクロは、読み書きするセルがソースの字だけで決まるときに動かし、実行のときに決まるなら動かさずに、そのことを伝える。
- **PDF の字の目印**：`page` がなくても、ページを順に配置して探す（時間の上限で止まっても、控えの続きから探す）。
- **表の取り出し・CLI の検査**：`read_table` は行を少しずつ読み、`out_path` に流して書く（`cursor` で続きも。`rows` で頼んだ範囲だけも）。`todoku audit` も大きな書類は分けて読む道で動く。
- **Access**：開くときは表ごとにページの表だけを作り（表・行の数・列の概要）、`read_window`・`read_table` の `sheet` と `rows` で頼まれた行のあるページだけを解く。ファイルをメモリに読まない。1 回に返す量のほかに上限はなく、どの表のどの行にも届く。

</details>

[`sources/`](../sources/) に記録してあり、同じものを取り直せる。取得は robots.txt に従い、1 件ずつ間隔をあけて行った。
