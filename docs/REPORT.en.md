# todoku: detailed report

How to use it, what each tool does, how each format is built, how to read the checks, and the conditions of each comparison. Full results are on the [portal](https://claude.ai/artifact/45P2GdSFYWkAqWrdLebmSH).

[日本語](REPORT.md)

**Summary**

- 935 government-site documents from 185 countries and regions were actually read and written after freezing the version (878 of them a new sample nobody opened before the freeze). Estimated documents read accurately: about 2.45 million; written accurately: about 2.38 million.
- The baseline count is an upper bound: a person picks the best tool per format and todoku points out the fields. Even so, baselines write 0 .doc and .xls files and read 0 .doc, .odt, .ods and .rtf files, and on .xlsx it is 29 to 11 for writing and 35 to 14 for reading. Requiring the original PDF bytes to be kept, documents written are about 2.38 million for todoku and about 1.92 million for the baselines.
- todoku proves, document by document, that nothing changed besides what it wrote and the resulting calculations. The baselines have no such proof.

### Known weaknesses

- **39 PDFs only todoku failed to write (of the 878):** about 5 correct refusals to protect certified signatures; about 15 written cleanly but misread by the checking OCR; about 12 written over photos or logos that are not fields; about 5 overlapping printed text; 2 hard to read (black on a dark background, clipped at the page edge). The breakdown was sorted by eye.
- **Non-fields offered as fields:** on documents that are not forms, photos and logos can be offered as places to write.
- **Hard-to-read places are still written:** text written into a PDF is compared with its background letter by letter, and a letter that has the same colour as its background is stopped as a read-back difference. Letters on a dark background, and letters that something drawn later covers, are written and reported with their position (mm), not stopped. Whether text on a photo or a pattern can be read is for the agent to decide with view_page.
- **Read grades that are too kind:** 19 documents graded S or A missed the accuracy bar: 5 Arabic PDFs (all characters present, bigrams .89–.97; baselines .47–.63), 4 .ods/.odt, 3 PDFs with text in images (one with character recall 0.2 graded A), 7 just under the bar (.989–.995).
- **Excel calculation:** full recalculation uses the same calculator as writing (checked against real Excel on 3 input variations, 306 cells). Functions with undetermined dependencies such as `INDIRECT`, `OFFSET`, `TODAY` are only counted. The big-workbook path was tried on 3 real files and on no .xlsm. When the whole-book calculation that runs after a big-workbook write (in another process) disagrees with the written values, the audit (audit_document) renames that file to `name.unverified.ext`: the rename happens when the audit is called, and until then the file keeps its name. When the file cannot be renamed (another program has it open, for example) the name stays and the result only says not to hand the file over (checked on built files only). Same-named checkboxes, drop-downs, list boxes, spinners and scroll bars on one sheet get ids with the control's position ("Check Box 1@B6", the same rule as option-button groups; a write by the bare name is refused with the candidates): none of the 2,975 controls in the 377 collected workbooks that open has such a clash, so this is checked on built .xlsx files only (.xls goes through the same rule, but no .xls with clashing names was built). ActiveX controls get no position (Excel keeps their names unique within a sheet).
- **105,256 cells:** the Niigata form is blank, so 87% of the results are empty values. 13,815 cells hold values, and all cells matched, empty ones included.
- **Legacy Word form fields:** fields that take no input, calculated fields and current-date/time fields are read from the field settings, shown as "not a place to enter", and not written without `force` (.docx, .doc, RTF). Word 6.0/95 .doc files are read without these settings. Number and date formats of a field (`#,##0` etc.) are shown as facts but not applied to written text. Calculated fields are not recalculated (when a written field is set to recalculate on exit, the result says so).
- **Reading text-only files:** the sample shown for each candidate encoding is the 48 characters at the first place where the candidates differ, so single-byte encodings can show identical samples (they differ elsewhere in the file). When the rules cannot decide a CSV/TSV delimiter, the agent reads the window and chooses one (`delimiter`: one ASCII punctuation character, or tab). The rules do not decide in two cases, both read B / write B: when two delimiters each split every one of the first 200 lines into the same number of columns (the window is read with comma or tab, and the column count under the other delimiter is told), and when none of ",", tab and ";" occurs in any line while another ASCII symbol (such as "|") splits every line into the same number of columns (the window stays one column, and the symbol and its column count are told; a symbol inside values, such as the "-" of dates, is just as even, so the rules do not decide). Rereading with the chosen delimiter does not lower the grade, and the reason "delimiter chosen by the agent" stays (marked "confirmed by rule" when the first 200 lines all split into the same number of columns, "cannot be confirmed by rule" otherwise). The choice applies to one call only, so it is passed to every tool for that file. In encodings where the second byte of a character can equal the delimiter byte (Shift_JIS "ポ" is 0x83 0x7C), a character is never cut in the middle (1,026 constructed files in 21 encodings compared between the two readers: 0 differences). Limits: none of the 81 collected CSV/TSV files is delimited by "|" or another such symbol (0 files get a candidate under the new rule), so this was verified only on constructed files. Evenness is counted on the first 200 lines (up to 200,000 characters). Encodings in which shift sequences change how the same bytes are read (the ISO-2022-JP family, ISO-2022-KR, HZ, UTF-7): a file whose bytes are all ASCII and that contains ESC is decoded strictly as ISO-2022-JP, JP-1, JP-2, JP-EXT, JP-3, JP-2004 and ISO-2022-KR in that order (and as Windows ISO-2022-JP if none of them reads it), and the first reading in which ESC really worked as a character-set switch (fewer ESC left in the text than in the bytes, no SO/SI left in the text) decides the encoding (CSV, TSV, .txt, JSON, JSON Lines, HTML, XML; grades are the same as for a UTF-8 file). Files with colour-code ESC or SO/SI that do not switch anything stay ASCII. HZ and UTF-7 use ASCII characters as their shift marks ("~{", "+"), so the rules do not recognise them; the agent chooses them with `encoding`. Reading by range reads a UTF-8 recoded copy (in memory up to 64 MB, a temporary file above that; the window says so), so characters, delimiters and quotes are the same as in the whole window, and delimiters other than ",", tab and ";" can be chosen. Writing changes only the bytes of the written place, after checking with the decoder that the new bytes read as the written text and that the bytes after them start in the same state as before. Where the written characters share a byte run with their neighbours (inside or right after a UTF-7 base64 run), that run is rewritten with the same characters. Where the bytes after cannot start in the same state (Hangul written before the ISO-2022-KR header ESC $ ) C when the header is not at the start of the file), the header is put before the written characters and the original bytes after them are checked, to the end, to read as the same text (before, these two kinds of place were refused). An original header left after them that no longer changes anything is removed, and a second header is not written inside the written characters (the file keeps one header). When ASCII would directly follow the header, SI is written first (Windows ISO-2022-KR, code page 50225, reads what follows the header as Hangul until SI even without SO; Python, iconv and perl read the same text with or without the SI). The whole written file is then decoded strictly, and if it is not the character-level replacement, nothing is written. A character that reads back as a different character is not written, and the refusal says which character it would become: Python's encoders turn some characters outside the table into the bytes of a near character (in Shift_JIS (CP932) the wave dash U+301C gets the bytes of U+FF5E; in EUC-JP the yen sign gets the byte of the backslash. Before, for CSV and .txt the file with the other character was written under the "unverified" name and the difference was reported, and for dBASE the other character was written and reported as verified. - **Files whose format neither the marks nor the name decide:** a file whose leading marks (PDF, ZIP, OLE …) and whose name ending do not decide a format is read as a text file when its content is only characters (before, it was refused as an unsupported format). The rule: the encoding is decided, or candidates are offered, exactly as for .txt, and the decoded text has no C0 control character (other than tab, line breaks, form feed and vertical tab) and no DEL. Words, meaning and line shapes are not looked at. If the text (after a BOM and whitespace) starts with `<?xml`, `<!DOCTYPE html` or `<html`, it is read as HTML/XML (write D); otherwise it is read and written like .txt (a window of lines; a write changes only the bytes of the written characters). Formats decided by marks or by name are decided first, as before. A file named .docx that has no ZIP mark and whose content is only characters (a notice saved in place of the document, for example) is read the same way. That the format came from the content stays in the window (`format.kind_by: "content"`, `kind_note`) and in the grade reason “format decided from the content” (read B, write B): whether some application shows or prints these characters as a document of another format (whether that format's commands appear as raw characters) cannot be known by rule, so the agent reads the text and checks. Large files are read in `paragraphs` ranges, and members of archives are read the same way. In the 1,890 collected files, 5 of the 6 files with no decided format are now read: French prose named `.doc` (400 KB, 6,499 lines), quoted tabular text named `.xls`, a fetch log, and two HTML pages named `.bin`. The remaining one is all NUL bytes. The format of the other 1,884 files is unchanged (as are the 13 members of the 5 collected archives). Speed: deciding the format of a 96 MiB text file takes 1.1 s (every byte is read once); refusing a 50 MiB file of random bytes takes 0.02 s. Limits: a call that passes no file name (the library's `kind_of(blob)`) does not decide from the content. A file with even one control character is refused (logs with colour ESC sequences, text mixed with NUL). A file no candidate encoding can read is refused, and passing `encoding` does not open it (the format is decided first). UTF-16 with no BOM and no NUL byte (a single line with no ASCII character and no line break) is not recognised. Bytes with no control character are shown as the characters a candidate encoding gives even when they are not text (short binaries such as “MZ” followed by 0x90; among random bytes, about 1 in 100,000 runs of 100 bytes has no control character; read B “encoding cannot be decided by rule”, with candidates). Other formats written in characters (PostScript, MHTML, FDF, DXF, base64 …) are read as their raw commands. HTML that does not start with `<!DOCTYPE html` or `<html` (a bare `<table>` saved under an .xls name) and XML without `<?xml` are read as text with tags. CSV content still becomes a window of lines (no cell fields, no `delimiter`, no `rows`). JSON and mail are not recognised from the content.

Otherwise the bytes do not decide the encoding: 6 multi-byte, 27 single-byte and 18 DOS encodings are tried in a fixed order; the listing uses the first one that reads every name cleanly, the other readings are listed as candidates with samples, and the window says the rules cannot decide (read grade B). When the agent reads the samples and passes its choice as `encoding`, the listing is redone in that reading and the grade is not lowered (the choice stays in the reasons; an encoding that does not read the names strictly is refused). DOS single-byte encodings read any byte as a character, so unlabelled names that are neither ASCII nor UTF-8-shaped are always "undecided" (a ZIP with Shift_JIS Japanese names is also read grade B until the agent chooses). Even after merging readings that give identical text, the candidate list can exceed 30 lines. Names in mixed encodings within one archive are shown in one reading only. A name that is also valid UTF-8 is read as UTF-8. A member can be addressed by its correctly read name without passing `encoding` (when exactly one member has that name under some reading). Writing does not change the name bytes. A 0xFF byte in an LZH name is read as a folder separator. .eml is read by its MIME charset declarations and does not take `encoding`. Embedded (OLE) object type names and package file names: the Unicode name if present; otherwise the code page of the summary information (`PIDSI_CODEPAGE`) in the same storage, then that of the outer file; with neither, the same decision as archive names, and the window says it is undecided. A type name appears in the window only for embedded objects whose content todoku cannot read, so the window text of the 844 collected documents is unchanged. 8-bit text in pictures (WMF, EMF) is read by the charset of the selected font. Text in a font whose charset names no code page (DEFAULT, etc.) is read by the same decision as archive names, and the picture output says the text is undecided. Of 252 pictures in the collected documents, non-ASCII 8-bit text occurs at 84 places in 12 pictures, all decided by the charset (81 Greek strings were half-width katakana before). The target file name of an .xls link (when there is no Unicode name) is read the same way and told (none of the 91 collected .xls files has such a link). Word 2 .doc files take the encoding from the document language number (Windows-1252 for languages not in the table). The readings for archives, mail and link targets were checked only with constructed files (the collection has no ZIP, tar, gzip or LZH with unlabelled non-ASCII names, and no .msg or .eml). Text in dBASE, Lotus 1-2-3 WK1 and Excel 2–4 .xls files follows the rule in the next item. Still guessed: when macros run, `Chr`, `Asc` and file I/O use Shift_JIS; the formulas `CHAR` and `CODE` use Shift_JIS or Windows-1252. Passwords are tried only as Unicode and Shift_JIS bytes. 8-bit PDF font names are read as UTF-8, then Shift_JIS. - **8-bit tables (dBASE .dbf, Lotus 1-2-3 .wk1, Excel 2–4 .xls): the encoding rule and its limits:** text (field names, text values, memos) is not assumed to be Japanese; one encoding is decided for the whole file (before, each string was guessed on its own — Shift_JIS if it read strictly, otherwise Windows-1252 — so Korean, Chinese and Cyrillic tables became unreadable text with nothing for the agent to choose, and one file could mix encodings string by string). The rule: if the file's declaration (.dbf: a sibling .cpg, otherwise the language mark in the header; Excel 2–4: the CODEPAGE record) reads all the text strictly, that encoding. With no declaration, or one that cannot read the text (the window says so), UTF-8 if all the text has the UTF-8 shape. Otherwise the bytes do not decide: the same order as archive names (6 multi-byte, 27 single-byte, 18 DOS encodings) is tried, the window is built with the first reading that reads everything cleanly, the other readings are listed as candidates with samples, and the window says the encoding of the values cannot be decided by rule (read B, write B). When the agent reads the text and passes the chosen encoding as `encoding` (window, fields, fill, audit, grade, and also `read_table`, `explain_calculation`, `try_calculation`, `extract_processing`), the file is re-read that way only if every string reads strictly, and the grade is not lowered (the choice stays in the reasons; unreadable or unknown encodings are refused). An encoding different from the declaration can be chosen (the declaration stays in the window). Non-ASCII text is written to a .dbf only when the encoding is decided: an undecided file refuses until the agent chooses (ASCII values can be written). A file with only ASCII text and no declaration takes the writing encoding from `encoding` (before, it wrote Shift_JIS). A .dbf value whose last character was cut by the field width (in the middle of a multi-byte character) is read up to the cut, and the window says it was cut. Limits: DOS single-byte encodings read every byte as a character, so a table with undeclared text that is not UTF-8-shaped is always "undecided" (a Shift_JIS Japanese table is read B until chosen; Shift_JIS is first in the order, so the window text is the same as before). Korean (CP949) text appears in an earlier encoding of the order (such as EUC-JP) until chosen. The candidates can exceed 30 lines. Lotus WK1 has no declaration, and the Lotus character set (LICS) is not a candidate. The .dbf language mark 0x57 ("ANSI": the code page depends on the machine that wrote it) is not a declaration. Two language marks with no Python table (0x68, 0x69) cannot be used. A .cpg may hold a code page number, a number after "8859", an encoding name, or "LDID/number". Text in mixed encodings within one file is shown in one reading only. A table embedded in a Word or Excel document does not receive the chosen encoding (it is read by rule). The collected files contain no .dbf, .wk1, .cpg or Excel 2–4 .xls (all 97 .xls files are Excel 5 or later): this rule was verified only on constructed files. Reading takes longer because every candidate encoding is tried: 0.33 s → 0.41 s on an undeclared 30,000-row .dbf (1.2 MB), 0.02 s → 0.03 s on a .wk1 with 8,000 labels (CPU time on the same machine). With a declared .dbf the difference is smaller than run-to-run noise.

In the .doc written by LibreOffice the change date is 1970-01-01 00:00 and the author name is empty (shown as stored: the date only). The author and date of Word 6.0/95 changes are not read (only the insertion and deletion marks). Paragraph-break and row changes are shown for .docx only (not for .doc, .odt or RTF). The large-.docx path reads only the chunks that hold revision elements and reports the same paragraph lists and the same reasons as the normal path (moved text and changes in headers and footnotes are counted too): the 108 collected .docx/.docm files give the same result on both paths, but none of them has an unaccepted insertion or deletion, so this rule is checked on built files only. Tracked changes in .doc were checked on one Word 97 file made with LibreOffice and on Word 6.0 files built to the specification: none of the 242 collected .doc files (225 opened) has an insertion or deletion that is neither accepted nor rejected (one file has tracking on; LibreOffice reads the same). Word 6.0/95 is written by overwriting character bytes, so text written inside an insertion stays inserted text (told per field). Format changes (and who made them and when) and, for .doc, deleted paragraph marks (changes that join paragraphs) are not told. Strikethrough and font colour are shown for .docx, .xlsx, .odt, RTF, .pptx, .hwpx and .hwp; PDF strikethrough (not a character format but a line drawn over the glyphs) is decided from the positions of the line and the glyphs and shown (see "PDF strikethrough: rule and limits" below). - **Limits of PDF layers:** visibility is decided from the default configuration (`D` of `OCProperties`: `BaseState`, `ON`, `OFF`), the usage switches for screen and print (`AS` with View, Print, Export) and membership marks (OCMD `P` and `VE`). The Zoom, Language, User and PageElement usages, other configurations (`Configs`) and the state after a person toggles layers in a viewer are not evaluated. - **Limits of underscore ("_") blanks:** in PDF, underscores narrower than one em become a place only when they stand in a row separated by spaces ("_ _ _ _") or chained by separators ("_/_/_"). A lone short underscore gives no place. A spaced row is one place, not one box per character (the written text may shrink to fit its width, and the result says so). An underscore run touching a name character ("Tel.____", "1____"; letters and digits of scripts that separate words with spaces, such as Latin, Cyrillic and Greek) is a "?" place; touching a script that can break lines inside words (UAX #14 line-break classes ID, CJ, H2, H3, JL, JV, JT, SA: Han, kana, Hangul, Thai and others; `chars.SPACELESS_SCRIPTS`) it is a rule field. Of the 835 collected PDFs, one has rows of short underscores (a Ukrainian form: two places, number and date).
- **Limits of labels for PDF places:** the label (name) of a place in a PDF without form fields (an empty cell or an underline rule) is taken from the nearest text around it, in a fixed order. For an empty cell: the text to the left (to the right in right-to-left text), above, to the right, the text of the same line (the parts before and after the place of a line that continues across it, in reading order around the place mark: "年［　］月"), then below. For an underline rule: the line at the same height to the left of the rule, the text to the left, the text of the same line, the text above or below when only one of the two exists, then the text to the right; when there is text both above and below, neither is chosen (some forms print the caption under the rule, others above it). There is no distance limit, so far-away text can become the label: which side the text is on and how many mm away is in the facts and on the window line of every place ("上「Application」11.5mm・同じ行の左「Name:」1.8mm"). When a line above or below is split by gaps of one em or more, only the parts that overlap the place horizontally are shown (the whole line is in the fact `line`); lines to the left and right are shown whole. Text below is never the source of the writing size (it can be a small note under the place). An underline rule in the middle of a line is listed after that line in the reading order, and its default writing size is the page's typical size. The label of a form field (AcroForm) without a description (`/TU`) is chosen from the text around it by the same rule as for places: a field inside a cell with text (more than half of the field's area lies in that cell) takes the cell's text (without the characters under the field); a field inside an empty cell takes the text around the cell; otherwise the text before the field on the same line, or the nearest text on each side of the field in the order left, above, right, same line, below. A checkbox takes, like a box glyph, the text right after it on the same line, or else the text before it. Text made only of box glyphs (the printed box under a field laid over it, or a neighbouring box) is never a label. The label of a radio group is the text to the left of all its widgets together, or else above (option texts and option lines are skipped). The value shown by a read-only text field (some forms place their captions as field values instead of printed text) counts as surrounding text, and `neighbours` says which field it belongs to (`field`); values of fields that are not shown on screen or paper, and of calculated fields, are not used. There is no distance limit: the side and the distance (mm) are in `neighbours`. Before, only text within 200pt to the left or 30pt above was used, and text to the right or below, text inside a cell seen from a field outside it, and read-only values were not. In the 835 collected PDFs (first 60 pages), the 8 files with form fields that open without a password have 264 fields (a radio group counts as one; 63 with `/TU`): the 130 whose label was the field name ("Text5", "Group9") are now 2 (read-only fields whose value is itself a caption), and the 27 whose label was the printed box glyph "☐" (21 checkboxes, 6 radio groups) now carry the option text or the question. Of the 182 fields that are not caption fields, the label comes from `/TU` for 40, printed text for 64 and a read-only value for 78. The number of fields, their ids, positions and option texts are the same as before. Limits: the label is the nearest text in a fixed order and is not always the right one. For the 142 labels taken from surrounding text, half are within 6.2mm, nine in ten within 62.8mm, and the farthest is 107.2mm (the lower rows of ten fields under one instruction). Where a read-only field showing only "$" sits right before an amount field, the label is "$" (the "Grant amount spent" to its left is not shown). A field in a table takes the row caption (left); the column caption (above) is in `neighbours`. The 201 labels were read as a list with their sides and distances, not checked against page images. The option texts of a radio group are still taken from the line at the height of each widget (up to 200pt). The end of the option text of a box glyph or checkbox: gaps inside a run of single characters joined by equal spaces ("氏　　名") do not end it, but that run used to end in the middle of a word ("可　　不可" gave "可　　不", "1 保護者の…" gave "1 保"); now a character directly followed by a letter or digit is not part of the run, and reading continues after the run up to the next gap. Of the 9,417 texts before or after box glyphs in the collected PDFs, 51 in 29 files changed (23 longer, 28 shorter; "年　　月　　日まで" becomes "年　　月"). In the 835 collected PDFs the places and their ids are the same as before (1,151,362 places). 7,700 underline rules that had no label now have one (left 1,454, same line 1,135, above 1,291, below 2,279, right 1,541; half of the texts below are within 8.3mm and nine in ten within 32.2mm, and on large drawing pages some are 600mm away), and 428 empty cells that had no label now have one from below (421) or from the same line (7). - **Limits of controls bound to document properties:** when the XML part a content control is bound to (`w:storeItemID`) is not among the document's customXml parts, the bound value is written only if the binding path (XPath) and its namespaces lead to exactly one element in exactly one of the document property parts (`docProps/core.xml`, `docProps/app.xml`); that property gets the same value and the result says so (the document's title, author and so on change). If the path leads nowhere, or into two parts, the write is refused. Custom properties (`docProps/custom.xml`) are not looked at.
- **Limits of spans that cannot be rewritten:** blanks and box characters inside text with ruby (base and reading), marks for pictures and embedded objects, footnote marks and equations cannot be rewritten, so they are not shown as places (for example the blanks inside a label "氏　　名" that carries a reading). In RTF, text written right after a footnote mark takes the format of the next character (at the end of a paragraph, of the paragraph mark). The kind of an object embedded in a .doc is taken from the ProgID its storage states (`\x01CompObj`); a storage without one is judged by the word in the EMBED instruction.
- **Limits of positions after characters outside the Basic Multilingual Plane ("𠮷", emoji):** in .xls (BIFF8) and .xlsb, the character count in the file and the positions of per-character formatting and phonetic readings are read and written in UTF-16 code units (such a character counts as 2: XLUnicodeRichExtendedString, FormatRun and PhRuns in MS-XLS). - **Limits of numbers and dates given as text for sheet cells:** a number given as text is read with "." as the decimal mark and "," as the three-digit group mark (the notation of JSON numbers and of the numbers the window shows). Spellings in another notation that have exactly one numeric reading ("1.234,56", "1.234.567", "1,5", "1 234,56", "1'234.56", "12,34,567.89") and digits of other scripts (any Unicode decimal digit: "١٢٣", "१२३" and so on; also the Arabic decimal, thousands and percent marks and the minus sign U+2212) are forms Excel takes as text, so they become numbers only in a cell with a number format, a cell a formula refers to, or a cell with a numeric validation rule, and the result says how they were read; in other cells they stay the text as given (never a number in a date-format cell). The shape "1.234", "10.000", "1,234" (one to three digits, "." or ",", three digits) differs by a factor of 1000 in regions where the two marks are swapped: it is read in the fixed notation, and the result says how it was read and how to give the other value (a JSON number). Nothing is said when the cell's format shows the same digits and marks as typed ("1,234" in a `#,##0` cell, "1.234" in a `0.000` cell): a person who means 1.234 in a comma-decimal notation and gives "1,234" for a `#,##0` cell gets 1234 written and is not told. A currency sign is any one Unicode currency symbol (Sc) before or after the digits (words such as "円" or "EUR" are not read). Bracketed negatives "(100)" and a trailing sign "100-" are not read (in a numeric cell the result says the value was written as text). Dates are read only in year-first forms ("2026-04-01", "2026/4/1", "2026年4月1日", "2026년 4월 1일", "2026.04.01.", and the same forms in digits of other scripts) and Japanese era forms ("令和8年4月1日", "R8.4.1": a leading M, T, S, H or R is read as a Japanese era). The year is read as a Gregorian year (Buddhist, Hijri and Minguo years are not converted). Month names ("April 1, 2026"), the Minguo era and combined date-time forms ("2026-04-01T10:00") are not read; in a date cell they are written as text and the result says so. Numeric dates that do not start with the year ("03/11/2026", "1.4.2026") are refused in a date cell. A date before the first day Excel can hold (1 January 1900; 1 January 1904 in a 1904-based workbook) is written as text and told (in .ods it is written as a date, with the ISO form as its cached text).
- **Limits of the overlap check for text written into PDFs:** whether written text overlaps printed text, rules or other written text, or leaves its field and gets cut, is checked with the box of each glyph outline. For characters whose font is embedded in the written file (the bundled Noto Sans JP, shaped scripts, embedded system fonts), the box comes from that font's outline. For non-embedded Helvetica (some extended Latin letters such as ş, ł, ę), it comes from Adobe's font metrics (AFM); a viewer that draws with a substitute font differs slightly. Non-embedded CJK fonts (Hangul, Simplified and Traditional Chinese) and the printed side stay on an estimated box (0.7 of the font size above the baseline). The writer moves the baseline when ink would leave the top or bottom of the field, and shrinks the text in 0.5 pt steps when the ink is taller than the field. The smaller size is told only below 60% of the original or below 6 pt ("Égjy" at 12 pt in a 14.4 pt-high place becomes 11.5 pt, untold). In one-character-per-cell fields, the size is set so the widest character's advance fits the cell. Between two written values, when both have outline boxes, an overlap of 1/4 or more of the smaller box is refused and a smaller overlap is told with its position (mm). A value with an estimated box is refused on any overlap. Letters that go below the baseline (g, j, y) written just above a rule produce a rule-crossing notice: writing "Égjy", "gj", "j" into the 116,128 places of 819 collected PDFs gives 4,330 such notices (1,253 with Japanese values). With Japanese values no writing position changes.
- **Rule and limits of the visibility check for text written into PDFs:** the page after writing is rendered at 100 dpi, only around the written widgets, and compared with the picture before writing. (1) If no pixel changes inside a widget's rectangle, it is a read-back difference; if the changed pixels of the whole rectangle have a contrast below 3:1, it is reported (as before). (2) For each drawn letter, the colour of the background just before the letter is drawn is compared, pixel by pixel, with the colour after the letter is laid over it: a letter whose every pixel stays the colour of its background is a read-back difference ("drawn but not visible"), and a letter with more than half of its ink on places with a contrast below 3:1 is reported with the ratio and its position (mm). (3) A letter whose colour just after drawing differs, on more than half of its ink, from the colour when the page is finished is reported as "something drawn later lies over it" with its position (other annotations, overlapping fields). Both the text drawn in form-field appearances and the values drawn into pages without fields are checked. When a field has several widgets on a page, every widget is checked (before, only the first). After writing into a static XFA form, the appearance of the PDF field with the same name is checked (before, it was not). Text is drawn in the colour of the field's default appearance (/DA): text fields, combo boxes, lists, and the check mark added to documents without appearances (before, always black; in the 24 collected forms, 274 of 1,652 widgets, in 5 files, ask for a colour other than black: #000080 in 272, red in 2). How it was checked: writing "検査 Ab1" into 703 places of 84 collected PDFs, 2,800 letters in 668 places are checked one by one: 0 invisible letters, 3 dark-background notices in 2 files (15 letters, all black text on a dark grey band or box, which the old rule did not report), 0 overlap notices (the other 35 places are the 8 reported by rule (1) and 27 in XFA forms without PDF fields). With and without the per-letter check, the check takes 99.4 s and 99.3 s for the 84 files. Built files confirm: letters on a black band (stopped), on a dark blue band (reported), on a thin line (not reported), under a later annotation (reported), and white text asked for on a dark field (not reported). Limits: the decision is made on todoku's own rendering (not on other viewers' pictures). A page whose font is not available here is not checked letter by letter (when no pixel changes, it is reported as not checked). Only letters painted with a plain colour are checked one by one: letters filled with a pattern and outline-only letters get rule (1) only. Things that are not letters (check and radio marks that were turned on, circles drawn around printed words, seal and signature images) are not checked letter by letter but over their whole rectangle (the widget for a mark, the outer box for a circle, the placed frame for an image), by the same rule as (1): if no pixel changes it is a read-back difference ("the mark was set but is not visible"), and if the changed pixels have a contrast below 3:1 it is reported with its position in mm (before, none of these were looked at). Turning on check and radio marks 1,712 times in 121 collected PDFs (at most 30 fields per file, files of 3 MB or less, stopped after 40 minutes), 1,362 marks of form widgets are checked: 0 invisible marks, 0 notices. A mark set in a static XFA form is also checked, on the widget of the PDF field with the same name: setting marks 155 times in the 9 collected static XFA forms, 155 marks are checked, 0 invisible, 0 notices. The check takes about 0.19 s per write (before 0.01 s: pages with marks were not rendered). Built files confirm: a black mark on a black band, a white mark on white, a mark under something drawn later, an image of the colour of the page (stopped); a mark and a circle on a dark ground, a pale image (reported); a black frame around the mark (not reported). Because the whole rectangle is looked at, a mark, circle or image that is only partly hidden is not found. When the glyph of the mark is not available on this machine (no ZapfDingbats face), the check does not go by the brightness of the grey placeholder box the renderer draws at the glyph's place; it goes by the mark's own colour and the ground inside that box before drawing: if the ground has the mark's colour everywhere it is a read-back difference, and if the contrast is below 3:1 everywhere it is reported (the shape is unknown, so nothing is said when only part of the ground has the mark's colour; if the font itself is missing and the picture does not change, it is reported as not checked). Marks that were already on and marks that were turned off are not looked at. Circles and images were checked on built files only. Translucent and pale images are reported as hard to see. A translucent thing drawn later is also reported as lying over the letters (they are not necessarily hidden). On photos and fine patterns the decision is by per-pixel contrast, which may not match how people read. Differences finer than 100 dpi are not seen. If rendering takes more than 15 s for a page or 45 s in total, it is reported as not checked. Dynamic XFA forms (no PDF fields) are not checked, because todoku cannot draw their pages. Values that todoku draws into pages without fields, and fields that todoku creates, are drawn in black.
- **The page picture of a PDF (`view_page` and the visibility check for written text): rule and limits:** the page picture is drawn by todoku itself. (1) A fill of a path whose rectangles of opposite direction overlap (a frame drawn as an outer and an inner rectangle in opposite directions and filled with `f`) leaves the overlap as a hole, as the nonzero winding rule says (before, each rectangle was filled by itself, so the inside of the frame was filled too: on 2 pages of one collected PDF, 57 % and 70 % of the page was filled solid; setting a mark in that form made the visibility check stop with a false "not visible"). (2) When a transparency group (a form XObject with Group /S /Transparency) is placed with an alpha below 1 (ca), each thing inside it is drawn with that alpha multiplied in (before, when the content set the alpha back to 1, it was drawn opaque). (3) When a thin filled rectangle (thinner side under 2 pixels) is aligned to the pixels, its direction is kept (before, all of them were given the same direction: when a thin rectangle of the opposite direction was filled in one path together with shapes that are not rectangles, holes were filled and fills became holes: thin holes in outlined characters, the shaft and head of an arrow). - **Limits of PDF clipping:** text and lines that are drawn on the page but lie outside the clip, and so are not visible, are not read as visible content. Only the bounding box of the clip path (`W`, `W*`, a form's BBox, the page box) is checked: what lies outside the box is decided as not visible; what lies inside the box stays visible, even if it is outside the clip's actual shape (a triangle, a circle). Hidden text is kept out of the reading order, labels, fields and the overlap check, and is shown per page in a section "text hidden by a clip" with its position in mm (no character is dropped; the grade does not change). Text that straddles the box stays visible. A glyph just outside the box (within half its font size) is hidden only when the outline of its embedded font lies outside the box; glyphs of non-embedded fonts stay visible. A space there (a glyph with no ink) goes with the glyph next to it in the same text object (BT–ET); a text object with only spaces stays visible. Straight lines and filled rectangles outside the box make no rules or cells, and those that cross it are cut to the part inside. Nothing is cut at the edge of the page (a line that runs off the page keeps its shape). Curves and partly clipped pictures are not cut (the picture keeps its full rectangle; view_image shows the picture before clipping). Text used as a clip (Tr 4–7) and clips with an empty path are ignored. - **PDF strikethrough: rule and limits:** a PDF strikethrough is not a character format but a line drawn over the glyphs, so it is decided from the positions of the line and the glyphs and shown after the text as "〔取り消し線：「text」〕" (the text is not removed; the page's `struck` lists the text, its line and its position). A line is taken as a strikethrough when it is a straight, non-white line (a stroke or a thin filled rectangle; horizontal for horizontal text, vertical for vertical text) that runs along the text through the middle half of the glyph box (within a quarter of the font size from the centre), is no thicker than a quarter of the font size, does not extend more than one character beyond the run of glyphs it covers, has at least half of its length over that run, and whose ends do not meet other lines or curves. A covered glyph is one with more than half of its width under the line. Blank glyphs that directly follow or precede the covered glyphs (drawn space glyphs, not blanks filled in from gaps) join the run when the line passes over them by the same rule (where the text was struck together with its spaces, the line is longer than the text). A dashed line counts as one line when its gaps are at most one character. Underlines, cell edges, table rules, highlight bands and cut lines that continue beyond the text do not match this rule. A line taken as a strikethrough is not offered as an underline place to write on. Not told: a line that continues more than one character beyond the text, diagonal lines, curves and lines inside images. A line through the middle of the glyphs that is longer than the text is not told as "possibly struck" either: the collected PDFs contain 614 such lines (73 files, 162 pages), 524 of them with ends that meet other lines and less than half of their length over the text (table rules, page rules). The 88 that are not clearly rules were checked on page images and positions: 3 are strikethroughs (the option words 「相続人」 twice and 「本人」 once, all in one guide); the rest are example text printed over rules, cut lines and leader lines, so a "possibly" mark on all of them would make valid instructions read as deleted text. One of the three (「相続人」) is now told because the space glyph right after the text lies under the line. The other two (the line spans the full width of the stacked options and is 1.3 and 1.7 characters longer than the text) are not told. Drawing order and whether the line is hidden under a fill are not looked at. A line drawn at the same position as a stroke of a glyph is told as a strikethrough. An end glyph that the line covers by half or less is left out of the range. Long struck text is repeated inside the mark. Why the text was struck (void, an option not chosen, a correction) is not decided. In the 835 collected PDFs (first 60 pages of each: 6,183 pages) there are 96 places in 17 files. All 96 were checked against page images: 93 are strikethrough lines over text, 1 is a line that coincides with a stroke of the glyph, 1 is a short line over a bullet "•", and 1 is a cut line made by drawing the line over text and spaces together (「き　り　と　り　線　印」: the line passes through the middle of the glyphs and the space glyphs, so it is told as a line over the text). The 12 places where a strikethrough line had become an underline place are gone, and the rest of the window text and fields is unchanged (0 differences). Vertical strikethrough does not occur in the collected documents and was checked only with constructed files.
- **PDF font colour: rule and limits:** the colour of PDF text is the fill colour in effect when the glyph is drawn (the stroke colour for outlined text). For each page, the colour with the most visible characters (spaces and invisibly drawn text excluded) is the "normal colour" (black on a tie), and text in any other colour is marked: when every character of a line (one line in a cell) has the same colour, "〔字の色 #FF0000〕" before the line; for part of a line, "〔うち字の色 #FF0000：「text」〕" right after that text (the same notation as Word and Excel; the text itself is unchanged). A page whose normal colour is not black says so in the page's `normal_color` and in the window (on such a page, black text is marked). The meaning of a colour (example, note, link) is not decided. Colours are read through the selected colour space: DeviceGray, DeviceRGB, DeviceCMYK, CalGray, CalRGB, Lab, ICCBased (by number of components), Indexed, Separation and DeviceN (the tint function is evaluated). Before, the colour space was ignored and only the number of components was used (a Separation tint of 1 was read as "white": text colour was not used then, but this affected the "white line" rule for strikethrough and ruling lines). Text drawn with a Pattern (tiling pattern or gradient) has no single colour and is marked "〔字の色（模様）〕". Values are converted to RGB: CMYK, ICCBased and Separation are converted by fixed formulas without ICC profiles, so they can differ slightly from the colour on screen. Colours that look almost the same (#000000 and #0D0D0D) are still marked when the values differ (there is no threshold for merging near colours). - **PDF text under fills and pictures: rule and limits:** text that is drawn on the page but lies under an opaque filled rectangle or picture painted later, and so appears neither on screen nor in print, is not read as visible text (before, it was read like visible text: the original sentence left under a callout of a filled-in example, or text under a white correction patch, was mixed into the reading order and the labels). - **PDF text of a size that is left out of the reading order: rule and limits:** glyphs smaller than 0.5 pt (including glyphs without ink: size 0, horizontal scaling 0, a text matrix without height) and glyphs wider or taller than twice the page are not put in the reading order or the fields; they are shown in the page's section "見えない大きさの字" (text of a size that cannot be seen), one entry per run of glyphs drawn together, with the top-left position (mm) and the font size (pt). Whether to read them as content of the document is the agent's decision, from the text and its place. Before, only the number of such glyphs was told ("not put in the reading order") and the text itself appeared nowhere in the window (the audit check for missed text did not count them either). Now the audit checks that this text is in the window too. Runs made only of spaces are not shown and not mentioned. How it was checked: in the 835 collected PDFs (819 opened, first 60 pages each), 8 pages in 7 files have glyphs of this size: glyphs with ink are 57 glyphs in 1 file (0.39–0.50 pt; 11 runs such as "※未就学のお子様の申込不要" and "※昼食代及び保険料として"), and the other 6 files have spaces only (their old count note disappears). No collected PDF has a glyph many times larger than the page or a glyph of size 0 (checked on built files: 0.2 pt, size 0, horizontal scaling 0, a matrix without height, 9,000 pt). The windows of these 7 files and of 70 files picked at random were compared with the previous version: 70 are identical, and the 7 differ only in this section and the old note. Limits: a run keeps the drawing order, and a gap between words made by positioning is not turned into a space. The 0.5 pt cut is the same as before: text of 0.5 pt or more, however small, is read like ordinary text, and its size is not shown (among the visible glyphs of the collected PDFs, 6,055 glyphs in 19 files are 0.5 pt or more and under 4 pt; 952 of them, in 1 file, are under 1 pt). The size is taken from the font size and the matrices (not from the height of the ink). The position of a glyph many times larger than the page can be outside the page (negative mm). This text does not change the grade.
- **PDF text drawn in an invisible mode and not on a picture: rule and limits:** text drawn with neither fill nor stroke (text rendering modes 3 and 7) that is not on a picture stays in the reading order, and its place (line by line, up to 12 lines) is told as "見えない描き方の字（画像の上にない字）" (read B). todoku does not decide whether it is search text laid over glyph shapes drawn as lines and paths, or text put in without being shown: the agent decides, comparing the place with the picture from view_page. Before, invisible-mode text was told only when it was on a picture ("OCR text"); invisible text not on a picture was read like visible text and nothing was told. How it was checked: in the 835 collected PDFs (819 opened, first 60 pages each), invisible-mode glyphs (spaces excluded) are 85,415 glyphs on 46 pages of 5 files. Glyphs not on a picture are 29 glyphs on 1 page of 1 file ("Powered by TCPDF (www.tcpdf.org)": a line that a PDF library adds as invisible text), and the read grade of that document goes from A to B. The other 4 files do not change. Built files: modes 3 and 7, text on a picture (only "OCR text", as before), text both on and off a picture, a line of which only a part is invisible, and more than 13 lines. Limits: "on a picture" means that the centre of the glyph is inside the picture's rectangle (1 pt of slack): text on a transparent picture or on an unpainted part of a picture is also told as "OCR text". Invisible text over glyph shapes drawn as lines and paths (outlined text) is told as "not on a picture" too. When the shape of the text shows through a colour painted later inside a text clip (mode 7), it is still told as invisible-mode text. The lines of the reading order carry no mark (the place is in the reasons of the grade).
- **PDF text in the colour of what is under it, and text drawn with opacity 0: rule and limits:** text whose fill colour is the same as the colour under it, so that it appears neither on screen nor in print (white text where nothing is painted, black text on a black band), and text drawn with fill opacity 0 (ca in ExtGState), stays in the reading order, and its place (line by line, up to 12 lines) is told as "下の色と同じ色の字（画面には出ない字）" and "不透明度 0 で描いた字（画面には出ない字）" (read B). todoku does not decide whether it is text erased by making it white, text put in without being shown, or search text laid over glyph shapes drawn as paths: the agent decides, comparing the place with the picture from view_page. Before, both were read like visible text: white text only got the mark "〔字の色 #FFFFFF〕" and whether it was visible was not decided; text with opacity 0 and black text on a black band got nothing. A glyph has the colour of what is under it when, going through what was painted before it and touches its box (advance width × font height), from the latest to the earliest, one of these holds: an opaque filled rectangle of the glyph's colour that contains the whole box is reached; or nothing is reached and the glyph is white (the colour of a page where nothing is painted). Text of the same colour and opaque filled rectangles of the same colour met on the way do not change the colour and are skipped. Colours are equal when their RGB values rounded to 8 bits are equal. If anything of another colour, or anything whose colour cannot be decided (a picture, a line, a fill that is not a rectangle, a shading, a see-through fill, a pattern fill, Type 3 text, text with a blend mode, content inside an optional layer), touches the box at all, nothing is decided (as before, the text is read as visible and gets the colour mark). When the same text is drawn again in the same place in a visible way (white-filled text with a black outline over it), it is visible text. The colour mark ("〔字の色 #FFFFFF〕") stays on such text as before (so lines after the 12 listed in the reason can still be found in the window). The page's "normal colour" is counted over visible text only, as before. How it was checked: in the 835 collected PDFs (819 opened, 6,183 pages, first 60 pages each), text in the colour of what is under it is 50 glyphs on 10 pages of 6 files, and text with opacity 0 is 1,886 glyphs on 1 page of 1 file. On these 11 pages the reading order, the fields and the colour marks are the same as before and only the reasons differ. The windows of the other 6,172 pages do not change at all. The read grade goes from A to B for 4 files and does not change for 3 (2 files already at B and C, and 1 large PDF whose page is not laid out when the file is opened: the reason appears when that page is read). Five places were compared with poppler's picture (200 dpi): the white "ステージ", the black "（" on a black band, the white "78" and the white "You must enter an institution'" do not appear in the picture. On the page with opacity 0 ("Mercado de combustível em Portugal" and so on) the same text is drawn as shapes and those shapes appear in the picture (search text laid over them). Built files: white text on a white page, text on black and red rectangles of the same colour, CMYK white, lines and rectangles that do not touch the text, white text on a white fill (told). White text on a black rectangle, red and black text where nothing is painted, white text on a #FAFAFA rectangle, a line through the text, white text over black text, outline-only text, text on a picture, a shading, a filled triangle and a see-through rectangle, text with a blend mode, text with opacity 0.5, Type 3 text (not decided). Only some letters of a word in the same colour, only the one letter crossed by the edge of a stroked rectangle left undecided, text merged by ActualText, text inside a Form XObject, and pages without candidates being read only once. Time: to the 147.3 s of CPU time for reading the content of the 6,183 pages of the collected PDFs, the second reading of the 273 pages with candidates adds 10.7 s and looking for candidates adds 1.3 s (measured separately within one run). The CPU time for building the windows of 160 files chosen at random (under 3 MB), measured twice each, alternating before and now: before 44.9 and 45.4 s, now 43.3 and 48.3 s. Limits: text whose colour differs slightly (#FEFEFE text on a white page) is not told. Because the glyph box is used, a line or a neighbouring glyph's box that touches the box without touching the ink also leaves the glyph undecided: in the collected PDFs, 12 white glyphs on 5 pages that lie where nothing is filled were left undecided (6 glyphs on 4 pages overlap the box of the neighbouring black glyph by 0.46 pt; for 6 glyphs on 1 page a paint whose colour cannot be decided touches the box). The ground colour is decided only from a single rectangle that contains the whole glyph box (text on a ground made of two or more rectangles, or of a shape that is not a rectangle, is not decided). Non-white text is examined only on pages where the text lies inside a filled rectangle of the same colour whose shorter side is more than 2.5 pt. "Nothing painted is white" is the PDF page model (printing on coloured paper is not considered). Opacity 0 is seen only as the fill opacity of text drawn by filling (text rendering mode 0): stroke opacity (CA), text placed at opacity 0 as part of a transparency group, and text removed by a soft mask (SMask) are read as visible text. The rule about the colour underneath applies only to text in the page content (not to text in annotation and form widget appearances). What is painted after the text is handled by the rule "PDF text under fills and pictures" above. Pages with candidates (white text, or text inside a filled rectangle of its own colour) have their content read twice. The collected PDFs contain few cases (10 pages and 1 page); the other cases were checked only on built files. The lines of the reading order carry only the colour mark, not a mark for "not visible" (the places are in the grade's reasons).
- **Limits of the after-write appearance estimates (wrapping, cell fit, page growth):** pages of Word, Excel and similar files are not rendered, so todoku estimates from widths and font sizes whether a write is expected to add lines to a paragraph, not to fit in a cell, or possibly to add a page, and says so (the write is not stopped). Paragraph lines are estimated for .docx, .doc, .odt, RTF, HWPX and PowerPoint. A written paragraph is one whose text differs before and after the write (independent of how the write was requested). The width is the table cell width, or the page (one column) width minus margins and indents; for PowerPoint the shape width (or that of the same placeholder in the layout or master) minus the text insets; for HWPX the line width Hangul left in the file. Character widths are estimated as one font size for full-width characters and half for others; per-glyph font widths are not read. There are three wordings: lines increase at the estimated width; the written text is close to the width and increases in software that measures text slightly wider; the text before the write was close to the width and increases in software that measures slightly narrower (the estimate may put the original at two lines where the document actually fits it in one). Page growth is reported when lines are expected to increase, together with the page count recorded in the original (.docx, .doc, .odt, RTF): the space left at the end of a page is not examined. HWPX has no recorded page count, and nothing is said for PowerPoint. For cells (.xlsx, .xls, .xlsb, .ods) todoku reports text expected to be clipped by a neighbouring cell's content, to overflow a merged cell, numbers expected to show as "###", and shrink-to-fit. Not estimated: Ichitaro (.jtd) paragraphs (no public specification of widths and sizes); whether text written into boxed form controls (.odt, HWPX) fits the box; RTF style (`\s`) contents, per-cell padding (`\clpadl` etc.) and text boxes; HWPX paragraphs in landscape sections, shapes or captions that have no line width left by Hangul; PowerPoint shapes set not to wrap, shapes with no stated width, vertical table cells, and table-style font sizes (when no size is stated anywhere, 18 pt is assumed and said so; the lookup order follows ECMA-376 inheritance and was not checked by opening files in PowerPoint); .ods justified, rotated, vertical and repeated-content cells, and row heights (assumed padding and size are said so). The overflow direction is decided from the alignment (left-aligned text runs to the right of the screen, right-aligned text to the left) and the cell's reading order (readingOrder in .xlsx, iReadOrder in .xls, iReadingOrder in .xlsb, style:writing-mode in .ods: a right-to-left cell is right-aligned even with general alignment), and in a right-to-left sheet the right of the screen is the direction of decreasing column numbers. For a general-aligned cell whose reading order is not right-to-left, the direction is not decided when the sheet is right-to-left or when right-to-left text is written: both neighbours are checked and the message says the text "may" be clipped (LibreOffice 26.8 right-aligned Arabic and Hebrew text even in a left-to-right cell and left-aligned Arabic text that starts with digits; Excel's alignment is not verified). The rule was compared with the text positions in PDFs drawn by LibreOffice (72 cells: 3 alignments × 3 reading orders × 4 kinds of text × 2 sheet directions): the 58 cells where the direction is decided are all on the same side, and the other 14 are left undecided. In the collected sheets only one .xlsx has a right-to-left cell format, always with an explicit alignment (none in the 91 .xls and 9 .ods files). The .xlsb reading order was verified only on a file built from the specification. The HWPX, PowerPoint and .xlsb estimates were checked only with constructed files and bundled samples (the collected files contain no Hangul-made .hwpx and no .xlsb). Writing a 61-character value into empty places of collected files (the first six per file), one at a time, gave a wrap notice for 204 of 216 writes in 36 .odt files (the other 12 are boxed form controls), 120 of 120 in 20 RTF files, and 325 of 339 in a sample of 57 Word files; a cell notice for 19 of 27 writes in 7 .ods files (the rest: 6 with empty neighbours where the text stays visible, 2 justified) and 32 of 49 in 9 .xls files. With a 4-character value, 106 of 686 writes in the same 115 paragraph-format files (including 1 HWPX and 1 PowerPoint file) gave a wrap notice. Four files (2 RTF, 1 .odt, 1 .ods) were rendered with LibreOffice and all matched the notice.
- **Shaping limits:** a character missing from the font (such as "." in a Thai font) is refused rather than taken from another font. The Arabic lam-alef ligature is not formed with some font versions (seen with Noto Sans Arabic on Ubuntu).
- **Countries and regions not measured (10):** Central African Republic, North Korea, Eritrea, Eswatini, Gabon, Guinea-Bissau, Micronesia, São Tomé and Príncipe, Tuvalu, Vanuatu. No government documents were found in the crawl. 247 strata with 50 or fewer candidates in the 161 countries are also unmeasured.

## Usage: as an MCP server

todoku is an MCP (Model Context Protocol) server. It works from any AI agent that speaks MCP.

**In Claude Code, install it as a plugin. It then works from every folder.**
The plugin brings the MCP server and the skill `shinsei`, the workflow for finding and filling in application forms.

1. Install the Python tool [uv](https://docs.astral.sh/uv/). It launches todoku; todoku itself runs on the Python standard library alone.

   ```
   curl -LsSf https://astral.sh/uv/install.sh | sh
   ```

   (With Homebrew: `brew install uv`. Supported on macOS; Windows and Linux are in beta.)

   On first run, uv downloads Python 3.11 (about 30 MB). To work offline, run `uv python install 3.11` first while connected.
2. Install the plugin inside Claude Code.

   ```
   /plugin marketplace add Ono-Katsuki/todoku
   /plugin install todoku@todoku
   ```
3. To move to the newest version, run `claude plugin marketplace update todoku` and `claude plugin update todoku@todoku` in a terminal,
   then restart Claude Code (the plugin's version is the repository commit).

**From an iPad or phone:** todoku runs on your computer, and documents stay there. Use Claude Code's
[Remote Control](https://code.claude.com/docs/en/remote-control) to operate the computer's Claude Code from an iPad.
Run `claude remote-control` on the computer (or `/remote-control` in an open Claude Code conversation), then connect to the session from the Claude app on the iPad
or from [claude.ai/code](https://claude.ai/code) in a browser. The computer's MCP server (todoku) and files stay available. Keep the computer on. (Available on Pro, Max, Team, Enterprise and similar plans. Not with an API key.)

Then just talk: "Find grants I can use as a bedridden person and write the application." "Put our office's details into this form."
Opened inside this repository, todoku also loads from `.mcp.json`. For other MCP agents, configure:

```json
{ "mcpServers": { "todoku": { "command": "uv", "args": ["run", "--quiet", "--no-dev", "--directory", "<path to this repository>", "todoku-mcp"] } } }
```

| Tool | What it does |
|---|---|
| `open_document` | Opens a document; returns the format, the number of input fields and the start of the window |
| `read_window` | Returns the window (Markdown). Large documents are requested by range (`pages`, `sheet`+`rows`, `paragraphs`, `records`). Following `next` (`cursor`) reads everything |
| `list_fields` | Lists input fields (label, type, choices, current value, writability, context of the row) |
| `fill_document` | Writes to input fields and exports under another name. Returns the proof, the read-back result and what to tell the applicant (`say_to_user`) |
| `audit_document` | Checks whether this document can be read and written completely and accurately |
| `run_macro` | Runs an Excel macro (button) and exports the changed cells with a proof. Yes/no prompts go to the applicant first |
| `grade_document` | The document's grade (read S–F, write A–D) and accessibility alerts |
| `read_table` | Extracts Excel and Access tables row by row under their header columns (merged cells spread as on screen, each value with its source cell; `rows` requests a range; exports to CSV; rows not returned from the used range are reported in `omitted_rows` as a count and row-number ranges) |
| `extract_processing` | Extracts a document's calculation as processing. **Use this to learn the calculation rules.** Folds same-shaped formulas into one rule ("D3:D100000 = B{row}*C{row}") and returns inputs, lookup tables, outputs, order, branches, macros and PDF calculations. `format: "python"` exports a verified `calculate(inputs)` module (see "Extracting processing as processing" below) |
| `explain_calculation` | Explains one value: traces the result back to its inputs in a formula written with labels |
| `try_calculation` | Computes a result from a set of values without writing the document ("What if I choose category II?") |
| `view_page` | Shows a PDF page as a rendered image (glyph shapes, lines, images, field appearance; `dpi` sets the resolution), with mm rulers. For reading scans, checking frames before writing and checking the look afterwards |
| `view_image` | Shows an image inside a document (by the id in the window's image list or by part name; `region` views a part at original detail) |
| `to_pdf` | Wraps an image file in a PDF. Write to the resulting PDF with `fill_document`, giving a frame in mm |

Example dialogue:

> Applicant: "Put the same office details as last year into this pay improvement plan."
> Agent: (`open_document` → `list_fields` → `fill_document` for everything known)
> "I filled in what I could. Form 2-1, office name: XX Welfare Corporation / postal code [123]-[4567] / address: … — 18 places in all.
> I read the written file back and confirmed the values match. The one thing I need from you is the addition category (I–V). Which is it?"

The same operations are available from the command line (`uv run todoku --help`).

<details>
<summary>Defenses against broken documents</summary>

The MCP server runs tool calls in a separate process (a worker). Each call has time and memory limits (`TODOKU_TIME_LIMIT`, `TODOKU_MEMORY_LIMIT_MB`). Past a limit, the worker is stopped and the call says so.

- **Windows (beta):** this split (passing pipes) is unavailable, so calls run inside the server. The limits are the budgets for inflating, rendering and items (`TODOKU_MAX_ITEMS`) plus a watchdog thread for time and memory. It stops at Python-level boundaries, so it does not interrupt a single operation inside C. The command line runs on the same budgets.
- **macOS:** the memory limit RLIMIT_AS is not enforced. Long calls also have their worker's memory watched from outside with `ps`. Whether `ps` works is checked once at server startup. Where it does not, the server reports that this watch is off and only the worker's internal watchdog remains.
- **Linux:** RLIMIT_AS is enforced even without `ps`. Only the external resident-memory watch stops.

In both cases the server reports this on standard error and in its description (instructions).

</details>

## Extracting processing as processing (`extract_processing`)

Take only the data from a document and the processing becomes the agent's guess. `extract_processing` hands over the document's calculation rules in a complete, structured form (the Excel family: .xlsx, .xlsm, .xls, .xlsb, .ods and others; PDF forms). It runs on the standard library alone. No value is decided by AI.

- **Rules:** same-shaped formulas (equal in R1C1) fold into one rule per block. Each rule returns `text` (`D3:D100000 = B{row}*C{row}`), `formula` (as written in the file), `a1`, `r1c1` (normal form), ranges read, cell count and exceptions (different formulas and overriding constants inside the range). An empty cell splits a block; when the range is filled and rule cells are the majority, the odd cell is an exception. Workbooks with many rows are streamed with no per-cell records (100,000 rows × 2 columns of formulas: 4 rules, under 24 MB of added memory).
- **Structure:** inputs (labels as the fact "text to the left and above", the rules reading them, data validation), parameters (value cells read by absolute reference), lookup tables (ranges read by VLOOKUP, INDEX, MATCH, XLOOKUP and others; contents returned as data with a `read_table` request), names, outputs (cells nothing reads), rule order (what is read comes first) and cycles (distinguishing true cell loops from running totals that compute in order), branch trees for IF, IFS and SWITCH, array formulas (kept as formulas, not expanded), references to external workbooks, volatile functions and places not statically knowable (an `OFFSET` height of `COUNTA(A:A)`, for example), hidden sheets, rows and columns used in calculation, and flows between sheets.
- **Macros:** procedure source, cells read and written (only where the text decides them: `Cells(i, 5)` is "E?", and otherwise "unknown"), when they run (`Worksheet_Change` and its watched range, buttons, shapes), procedures called, and the relation to rules (whose inputs they write, whose results they overwrite).
- **`format: "python"`:** exports one `.py` with `calculate(inputs: dict) -> dict`. It depends on neither todoku nor anything outside the standard library. Calculation behavior (rounding, dates, errors) is cut from the engine's source, only as much as is used, so no hand-kept copy of those rules exists. An output that depends on a function it cannot compute raises an exception stating why (`NotReproducible`) (`outputs` selects other cells; `on_unknown="mark"` marks them).
- **Verified before returning:** the exported module runs in a separate process (`python -I -S`, with todoku unimportable), and every formula cell is compared against both the saved value and todoku's calculation. The result is `verification`: match rate, all mismatches (in a separate file when many), and `proven`/`mismatch`/`not_proven` per rule with reasons. Rules that depend on volatile functions, cells without saved values and rules that cannot be reproduced are reported per rule as not verified.

Measured on development forms: of 13 Excel files from Tokyo's 23 wards such as Katsushika and Sumida, 1 contains formulas (42 cells → 42 rules, 100% match; the rest have no formulas). The 9 files in corpus/forms: 149,630 cells → 1,383 rules (largest workbook 105,256 cells → 203 rules). Matches against both saved values and todoku's calculation are 100%. Against values computed by real Excel, with inputs varied 3 ways across 306 cells, there is no difference.

One value's explanation is `explain_calculation`. What-if calculation is `try_calculation`.

<details>
<summary>Extraction coverage (<code>limits</code> in the result) and PDF forms</summary>

Conditional formatting and data validation are listed as their own rule types (not part of the Python export). PivotTables, Power Query (M source) and data connections are shown as "processing that cell formulas cannot express", with definitions only (source range and fields); the calculation is not reproduced (.xlsx, .xls and .ods are read to the definition; .xlsb only reports that a pivot exists). INDIRECT and OFFSET dependencies are not statically knowable (the module computes with the actual references). When a dynamic array's result changes size, its spill range changes as in Excel.

For PDF forms, calculation order (/CO) and rules between fields (`AFSimple_Calculate`) are returned in the same form and exported to Python. Custom JavaScript and simplified field notation are shown as they are and marked as not evaluated (`evaluated: false`).

</details>

<summary>Placing seals and signatures, and the proof</summary>

**Only with the applicant's explicit consent** (nothing is placed without `"consent": true`), the applicant's seal or signature image (PNG, JPEG) goes on

**PDF text is written only with glyphs that can be drawn.** Glyphs from the bundled font (Noto Sans JP Regular, SIL OFL 1.1) are subset-embedded, so the text looks the same on machines without the font. A character that cannot be drawn is refused with a reason, never written as a blank.

<details>
<summary>Glyph routes and digital signatures</summary>

For characters in the bundled font (Japanese, Latin, Greek, Cyrillic, Vietnamese and others, 16,732 characters), only the written glyphs are embedded, regardless of word or language (usually a few KB to a few tens of KB added).

Characters outside the bundled font take these routes, per character, and are recorded in `fonts_not_embedded`:

- Latin extensions such as ş ğ ł ř ő use Helvetica (WinAnsi plus the Latin extensions in the standard 14 fonts' glyph tables).
- Hangul, Simplified Chinese and others use non-embedded CID fonts, only where the CMap (Adobe's public mapping tables, `scripts/make_write_cmaps.py`) gives a glyph within the declared character collection's supplement.
- Characters in neither embed only the written glyphs from a TrueType font on this computer (Arial and others; set with `TODOKU_PDF_FONT`; an empty value embeds nothing, the bundled font included), after checking the font's embedding permission.
- In documents declaring PDF/A, the computer's font is tried before non-embedded fonts.
- Arabic, Hebrew, Indic scripts and Thai are shaped by todoku (form selection, reordering, mark positioning) and drawn with glyphs from the computer's font. The check here compares the drawn glyph sequence with todoku's own shaping; it does not check the look itself. Those fields therefore get write grade B, and the agent checks the image with view_page (`check_visually` in the result).

Proof and read-back reread not only the value (/V) but the appearance (/AP) text, confirming that every character has a drawable glyph and is the character meant to show.

**Digitally signed PDFs** are written only within what the signature allows (no writing to locked fields or under certifying signatures that forbid changes; no new fields or ○ under signatures that allow only filling). When a signature exists, the applicant is told the write will show as a "change after signing".

</details>

## Facts from the tool, judgment from the agent

todoku decides only what specifications decide (the rules of ECMA-376, MS-DOC, PDF 32000, Unicode and others) and the guards against damage (proof, read-back, refusing clear overlaps).
What specifications leave open (which text labels a field, whether a place is for writing, how to align) is never decided by word lists or by numbers tuned to a corpus. The window and field list give the facts; the agent reads them and decides.

<details>
<summary>What is reported as fact</summary>

- **Labels** are the printed text, uncut. Table cells report the text to the left and above (`row_label`, `column_label`) and the number of cells between;
  Excel reports nearby text and its distance (`near`: cell count and mm). Text not directly adjacent is not shown as a label, but as "E12 ('氏名', 3 columns to the left)".
  PDF empty cells and underline rules report the nearest text to the left, above, to the right and below, and the parts before and after the place of a line that continues across it (`line_left`, `line_right`), each with its distance in mm.
- **"?" places** come with the place's text, character count, approximate width, text before and after, and the character count of spaced-out runs (`facts`).
- **Place ids are determined by position.** Inside paragraphs of Word-like window formats (.docx, .doc, .rtf, .odt, .jtd, .hwpx, .txt, .pptx):
  `P<paragraph>.c<characters before>` (5 printed characters before gives `P12.c5`). Inside Excel cells: `Sheet!B3@<position>`. These are not sequence numbers,
  so they stay the same as other places come and go, and after writing to earlier places. PDF uses `p{page}.{structure letter}{left}-{top}` (mm; `t` empty cell,
  `m` row of empty cells, `g` gap within a line, `b` box characters, `u` underline rule), with facts in mm too (`rect_mm`, `width_mm`). Empty cells in a grid
  are grouped by their x and y sequences; space below or above text in a cell shows as "[↓余白 12.0 mm]".
  Old sequence ids in Word-like formats (`P12.1`, `P12.a1`) are accepted only when they certainly point to the same place
  (when the paragraph has exactly one place of that kind).
- **Check values** accept only `true`/`false` and the state values the field declares (PDF state names, XFA values, box characters).
  Words like "yes" or "有" are not reinterpreted (turning the applicant's answer into true/false is the agent's job).
- **The meaning of a written value** is stated by the agent: `{"value": value, "as": "date of birth"}` (not written to the document). In the dialogue list it reads
  "date of birth: 昭和60年4月1日 (p1.t45-112 / nearby text "住所")"; without `as`, "p1.t45-112 (nearby text "住所"): …", so nearby text is never presented
  as the field's name. Dialogue is how the applicant checks, so `as` is always passed for documents the applicant checks (omissions go to `written_without_as`).
- **Inserting before or after text:** Word, Excel and others work as PDF does, with `{"@1": {"before": "年", "occurrence": 2, "value": …}}` and `{"@1": {"after": "氏名", "value": …}}`.
  todoku does not add places by word rules where a paragraph or cell starts with text.
- **Word's ○** defaults to a character border (`w:bdr`; a □ shape, but as a character format it does not shift). Word does not save text positions on the page, so an ellipse shape
  shifts between renderers (only with an explicit `"style": "ellipse"`; the result says which was used).
- **Placement and range** are the agent's too: PDF `align` (left, center, right), `pad_mm`, `box`; for text-anchored writing in Word,
  the `near` range (`near_paras`). The defaults (left-aligned, same line or same passage) are a starting point when nothing is decided.
- **Look after writing:** for PDF, `view_page` draws glyph shapes, lines, images and field appearance as on the page, and the agent looks at what it wrote
  (non-embedded fonts use a substitute, missing glyphs show as gray squares, images that cannot be decoded as gray frames, and the result says so).
  Excel, Word and similar files are not rendered, so wrap and overflow estimates (marked as tentative when based on values the document does not state) and the list of written content
  (including unselected choice groups and the count of remaining "?" places) are checked in dialogue.

</details>

## What is verified

### Can everything be read and written accurately (`audit_document`)

1. **Nothing missed in reading:** a reader separate from the window builder picks up every character in the file and confirms each one appears in the window.
2. **Every field is writable:** test values that satisfy data validation are written to all input fields the window shows, at once.
3. **Proof:** without using the writer's internals, both files are reread, confirming only the written places (and their calculated results and appearance) changed.
4. **Read-back:** the written file is reread, confirming the written values appear unchanged.

### Excel: nothing changed except what was written and its calculated results

Writes to .xlsx, .xlsm and .xls pass two checks. The coverage comes back as counts in `proof_scope`.

- **Dependency check:** from the formula text (other sheets, ranges, defined names, tables, shared formulas, array formulas), the cells that depend on the written cells are found without calculating. Any non-dependent cell whose value or formula differs from the original fails the proof.
- **Whole-workbook calculation:** the written file is recalculated in full and compared with its saved values. A difference in a dependent cell fails. A cell found non-dependent that changes with the written value fails as a missed dependency.

For a large workbook, if the full calculation does not fit the time limit (`TODOKU_CALC_SECONDS`), the result comes back as `deferred` (unverified). Pass the exported file to `audit_document`: it calculates the whole workbook in a separate process and returns the result in `written_proof`.

<details>
<summary>Reading <code>proof_scope</code></summary>

- `not_dependent`: cells that do not depend on the written values, and how many matched the original.
- `dependent`: dependent cells, and how many changed.
- `undetermined`: cells whose dependency cannot be decided. Formulas whose references are computed (INDIRECT, OFFSET, range operators and others) and functions that change on every open (TODAY, RAND and others) are counted, not guessed.
- `recalculated`: the full calculation's result. `checked` and `same` (cells compared and matched), `cannot_calculate` (cells not compared because they cannot be computed), `stale` (cells not yet reflecting the written value, such as those with a recalculate-on-open mark).
- The full calculation is separate from the writer's partial calculation and reads every row. It uses the same `formula/` engine, so function implementations are checked separately, in full, against Excel's saved values.
- For large workbooks, the dependency check compares the original and written sheet XML (without the writer's index).
- If `written_proof` has `problems`, the file does not go to the applicant.

</details>

### Grades: read (S–F) and write (A–D)

| Read | Meaning | | Write | Meaning |
|---|---|---|---|---|
| S | The data itself (CSV, JSON) | | A | Writable as it is (fields marked by the creator) |
| A | Readable accurately by rules alone (built-in date formats whose look varies by locale are shown in locale-independent ISO 8601, and the result says so) | | B | Writable after analysis (inferred from layout, "?" in the window judged by the agent, written after choosing an encoding) |
| B | Accurate when an agent reads it (everything is in the window; what is undecided is decided by the agent from the window's evidence: encoding candidates, calculated results saved by software other than Excel, paragraph-number formats that cannot be reproduced) | | C | Entered through a screen (UI) (button macros, e-application screens) |
| C | An agent can convert it with effort (macros, formulas that cannot be verified, window omissions, unreadable as any encoding) | | D | Not writable (no access; signatures, seals, thumbprints, notarization and other manual steps) |
| D | Needs the agent's interpretation | | | |
| E | A format agents are not good at (scans, image-only sheets, documents whose content is images) | | | |
| F | No access | | | |

The read grade is decided by reading content alone (finding input fields belongs to the write grade). If content picked up by the separate reader is missing from the window
(a miss in `audit_document`), the read grade is C, not A or S. When a text-only file reads under several candidate encodings,
the window lists candidates and samples; passing the agent's choice as `encoding` rereads the file in that encoding (the choice stays in the reasons).

Grading uses either "rules certain from the file's structure" or "the agent's judgment after reading the window", never word matching.
The word "押印" (stamp) in a document may be part of "押印不要" (no stamp needed). Things whose meaning matters, such as stamps, handwritten signatures and e-application screens,
are posed by todoku as questions, and the agent answers after reading the window. Grades are not rankings. They show how to handle a document so it gets through.

### Accessibility alerts (separate from grades)

Images without a description (alternative text) do not reach people using screen readers (WCAG 1.1.1).
For each image in PDF, Word, Excel, PowerPoint, OpenDocument and RTF, todoku checks for a description or decorative mark, and reports images without one as alerts with their location (page, paragraph, nearby text).
Agents do not guess at image content. They tell the applicant the location.

## Large documents

Large documents may be read in smaller amounts, but they are never treated as unreadable. When the estimated window exceeds `TODOKU_CONTEXT_BUDGET_CHARS` (400,000 characters, the size that no longer fits a 200,000-token conversation), `open_document` returns an overview (size, pages, sheets, rows, what is where), and the agent requests what it needs by range. Small documents work as before.

<details>
<summary>Reading and writing per format</summary>

| Format | Read | Write |
|---|---|---|
| CSV, TSV | `rows`. The file is not loaded into memory (line-position index). Empty cells by range | Only the written rows' bytes are replaced and copied. Proof: comparison of written rows and hashes of unchanged ranges |
| JSON Lines | `records` (unreadable lines shown as raw text) | Same |
| .txt | `paragraphs`. Very long lines are split by character range and marked (id `P<line>.x<position>`) | Same |

| PDF | `pages`. Only the page tree is read; only requested pages are laid out | Only pages being written are laid out (incremental update) |
| Word (.docx) | `paragraphs`. document.xml is streamed, keeping only an index of paragraph and table positions; a small document of just the requested part goes through the window reader (numbers and ids match the whole) | As usual (reads the whole) |

</details>

<details>
<summary>Continuation, limits and records</summary>

- **Continuation:** every result carries the range read (`covered`), the remainder (`remaining`) and how to continue (`next`). Following it to the end reads everything. `list_fields` works the same way.
- **Size of `list_fields` results:** when an MCP result does not fit `TODOKU_RESULT_CHARS` (25,000 characters, sized to Claude Code's limit of 25,000 tokens), the facts needed for writing stay (id, label, type, choices, value, row context, writing rules), evidence (`near`, `evidence`, `why` and others) is dropped, and `omitted` states what was dropped and how to request it. `ids` returns all facts for those fields; `detail: true` returns all fields unabridged, in parts. What still does not fit continues through `next`. Python API and command results do not change.
- **Grades:** low-cost checks run on the whole; remaining checks are listed in `deferred` ("unverified: reading omissions across all pages" and similar). Grades are not decided from samples.
- **Long lines and long cells:** `list_fields` on long .txt lines examines 2,000,000 characters per call and continues with `next`. For a very long CSV cell, the list cuts the value at the first 2000 characters, with `value_chars` and `value_cut` stating the cut (`read_window` has it all).
- **Audit:** `audit_document` is a long job. It is not bound by one call's time, returns progress on each call, and resumes from its record after stopping (records in `~/.cache/todoku/jobs`, changeable with `TODOKU_JOBS_DIR`).
- **Records and personal information:** long-job records (saved `.window` files, audit results, what-if values) contain document content. They live in a private location (0700) and are deleted `TODOKU_JOBS_TTL_HOURS` (24 hours) after the last write. Deleting the original file deletes its records. With `0`, windows are deleted once read and job records once results are returned (unread records after 1 hour; large documents are rebuilt on each open). `todoku forget` deletes everything except running jobs at once. Deletion happens at todoku's next call or server startup, so use `todoku forget` when you want nothing left after you stop using todoku. Passwords are never written to records.
- **Limits:** these stop broken or malicious files. Inflation is measured as a ratio to compressed bytes (`TODOKU_MAX_INFLATE_RATIO`, 200×); the memory limit is 1/4 of physical memory (`TODOKU_MEMORY_LIMIT_MB`). No file is refused for size alone (files over `TODOKU_MAX_FILE_MB` are memory-mapped; PDF incremental updates stream the original bytes too). A stopped call reports a smaller range to request instead (`smaller_request`).
- **Large embedded tables:** Excel workbooks embedded in Word that do not fit the window (`TODOKU_CONTEXT_BUDGET_CHARS`) are not parsed on opening. Passing `sheet: "E1!Sheet"` and `rows` to `read_window` or `list_fields` parses just those rows (following `next` reads everything). Field names for writing do not change. The audit (`audit_document`) reads it all. Documents whose window build exceeds the time limit become long jobs (`jobs.py`) that return progress.
- **Large arrays:** arrays that fit a sheet (`SEQUENCE(1048576,16384)`, `ROW(1:1048576)*COLUMN(A:XFD)`, `EXPAND`, `TEXTSPLIT`, `MAKEARRAY` and others) are held as a "row, column → value" calculation with no cells created, and only requested cells are computed (beyond the sheet, `#NUM!` as in Excel). Aggregates such as sums, counts and maxima are answered by formula for arrays of known shape (polynomials of row and column numbers), and otherwise read in order, bit by bit. When no cell value or partial sum is exactly representable as a double, values are added in Excel's row order (matching real Excel to 15 digits). Sums over arrays beyond 260 million cells (a size Excel cannot hold) return the exact value and say so. Aggregates that do not finish in time report progress and how to continue (`cells` in `try_calculation`: continues from the record in a separate process; `TODOKU_CALC_SECONDS`).
- **Range places:** when data validation, formula references, tables, array-formula ranges or OpenDocument repeats are wide (one declaration over 16,384 cells), they are not listed cell by cell. They keep the same facts as "`S!C5:C40000` (39,996 empty cells, read by formulas, data validation …)" (the window's range places, `range_places` in JSON, `kind: "range"` in `list_fields`). Every cell inside can be read and written by address. `list_fields` with `sheet` and `rows` returns those rows cell by cell (for tables embedded in documents, `sheet` is `E1!Sheet`).
- **Size for the split-read route:** documents with under `TODOKU_LAZY_MIN_KB` (4 MB) of content bytes build the window first and then split it. On the split route too, following to the end gives the same lines and field ids as the whole window; this is checked per format (tests/test_lazy_more.py). Only the "?" mark on cells referenced by formulas on other sheets depends on reading those sheets, so large workbooks may lack it (the cells are writable by address).
- **Rest of .xlsx:** text anchors without `near` search shared strings and rows and then write. ZIP64 and sheets with out-of-order row numbers are readable (writing takes the read-the-whole route; ZIP64 with a 64-bit central directory is read only, and writes are refused with a reason). Macros triggered by value changes run when their cells are decided by the source text alone. If decided at run time, they do not run, and the result says so.
- **PDF text anchors:** without `page`, pages are laid out in order and searched (stopping at the time limit resumes from the record).
- **Table extraction and CLI audit:** `read_table` reads rows little by little and streams to `out_path` (`cursor` continues; `rows` limits the range). `todoku audit` also takes the split-read route for large documents.
- **Access:** opening builds only each table's page table (tables, row counts, column overview). `read_window` and `read_table` with `sheet` and `rows` decode only the pages holding the requested rows. The file is not loaded into memory. Apart from the amount returned per call there is no limit, and every row of every table can be reached.

</details>
